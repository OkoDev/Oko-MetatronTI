## 1. Архитектурный и технический аудит

### Паттерн и модульность
Базовая декомпозиция `core/` (бизнес-логика без aiogram) ↔ `bot/` (UI) ↔ `web/` (дашборд) ↔
`strategies/` (Strategy Pattern) выбрана **верно** для монолита такого размера. Разделение слоёв
реальное: `core/` не зависит от aiogram, детекторы тестируются изолированно.

**Артефакты-призраки внутри монолита:**
- **Две параллельные архитектуры.** Боевая: `bot_with_subscriptions.py` → `bot/core/bot.py` →
  `core/*`. Мёртвая: `bot/main.py` → `infrastructure/` + `presentation/`, где файлы
  (`infrastructure/bingx/client.py`, `presentation/keyboards/adapter.py`) — 8-строчные
  ре-экспорты из `core/`. Это скелет несостоявшейся Clean-Architecture-миграции (~300 строк
  мёртвого кода). **Удалить или достроить.**
- **God-objects.** `web/dashboard_server.py` — **2498 строк** (HTTP + обработка данных + HTML).
  `core/trading_intelligence.py` — 1103 строки (после ARCH-02). `scripts/backtesting_engine.py` —
  1645 строк и **дублирует** логику симуляции вместо переиспользования `trade_simulator.py` →
  расхождение бэктеста и продакшена встроено архитектурно.

### Узкие места (Bottlenecks)

| Узкое место | Локация | Эффект |
|---|---|---|
| SQLite без WAL и `busy_timeout` | `subscription_manager.py:28`, `trade_simulator.py:95` | `database is locked` при параллельной записи `scan_loop` ↔ `trade_tracker_loop` |
| Синхронный SQLite в event loop | `trade_simulator.py:609–818` (5+ `sqlite3.connect()` в `check_open_trades_with_tsl()`) | блокировка loop на десятки мс ×N открытых сделок |
| Синхронный pandas/numpy в корутинах | `indicators.py:136–170` (`calculate_trend` — Python-цикл по 200 барам) | нет `run_in_executor`, CPU-bound сериализует loop на 600 парах |
| `enableRateLimit: False` | `data_collector.py` | намеренно (скан 30 мин → 30 сек), но rate-limit переложен на `Semaphore(20)` → риск бана IP при росте парка |

### Инфраструктурные риски / SPOF
- **SPOF уровня «личный ноутбук».** Запуск через хардкод `C:\Users\yogoru\...\Python312\python.exe`
  (`whats-next.md:135`).
- **Доказанный отказ из-за времени.** Инцидент **#1910 (APR/USDT)** (`current_state.md:3–12`):
  сделка застряла `OPEN` при −21% ниже SL, реализовав **−9.74R вместо −1R**, потому что часы Windows
  ушли на +3ч и фильтр `df[time >= created_at]` вернул пустой DataFrame → SL **не проверялся**.
- **Нет graceful shutdown** (`bot/core/bot.py:107–115` — `create_task` без отмены/`finally`).
- **`scikit-learn` отсутствует в `requirements.txt`** → чистая установка ломает `ml_predictor.py`.

### Технический долг
WT-порог `±60` захардкожен в **20+ местах** `divergence_detector.py` параллельно с `config.yaml:56–57`
(раздвоенный источник правды); `_last_signal` и счётчики растут без TTL.

**Вердикт:** выше среднего для pet-проекта, ниже порога production.

## 2. Сильные стороны и уникальные инженерные решения

1. **`core/api_engine.py` — production-grade транспорт.** LRU-кеш с эвикцией (`maxsize=5000`),
   `CircuitBreaker` (CLOSED→OPEN→HALF_OPEN), retry+exponential backoff (раздельный для
   NetworkError/RateLimit), **in-flight deduplication**, единый `Semaphore(20)`.
2. **Замкнутый контур «сигнал → симуляция → обучение».** Каждый сигнал → `simulated_trades` с
   feature-снимком → трекинг по OHLC → исходы переиспользуются для адаптивных весов и ML.
3. **MFE-трекинг** (`max_R_possible`, `captured_R_pct`) — измеряет упущенный потенциал движения.
4. **Quality Gate (Этап 8.4).** Единый `snapshot_time`, hard/soft таймауты,
   `analysis_quality = full|degraded|timeout`, no-silent-fallback.
5. **Систематический research-контур** (`scripts/analyze_wt_typeB.py`) — гипотеза → бэктест → находка
   → внедрение.

Это и есть технологический ров проекта — **при условии вычистки методологии бэктеста (§3)**.

## 3. Слабые стороны и критические уязвимости

### 🔴 ML / Data Science — фундаментальные методологические дыры
- **Selection bias в `RPredictor` (верифицировано).** `r_predictor.py:94–97`: фильтр
  `WHERE max_R_possible > 0` исключает сделки без потенциала. Таргет (`r_predictor.py:107`) =
  `max_R_possible` — это **MFE-метрика «идеального» выхода**, а не реализованный R. Результат идёт
  в **Kelly-сайзинг** → систематическое **завышение размера позиции** (реальный
  `captured_R_pct` ≪ 100%).
- **Дефектная валидация (верифицировано).** `outcome_predictor.py:133`, `r_predictor.py:68` —
  `cross_val_score` со стандартным K-Fold вместо `TimeSeriesSplit` → перемешивание прошлого и
  будущего на автокоррелированных рядах. **CV AUC = 0.56 ≈ случайное угадывание (0.5)**, и даже это
  завышено.
- **Мёртвый признак.** `predict_win_prob(... regime=None)` (`trading_intelligence.py:691`,
  `ml_enhancer.py:138`) → one-hot режима всегда `[0,0,0,0]` (4 из 12 признаков нулевые на инференсе).
- **Искажение базовой ставки.** Обучение только на `status IN ('TP','SL')`
  (`outcome_predictor.py:201`) — `TSL`/`EXPIRED` исключены.
- **Слабый ML влияет на решение.** При AUC≈0.5 P(win) подмешивается в
  `confidence = 0.7×orig + 0.3×P(win)` → шум в решении о входе.
- **Multiple-testing в бэктесте.** `analyze_wt_typeB.py` перебирает корзины `div_strength/gap/depth`
  и выбирает лучшую (3–20) постфактум без поправки → подгонка под историю.

**Главное доказательство несостоятельности — разрыв бэктест↔реальность** (`whats-next.md:207`):
заявленный WR `wt_b` **85%** vs реальные `wt_signal` **33.6%**, `pivot_reversal` **47.9%**. Бэктест
`wt_signal` ~49% → реальность 33.6% — **−15 п.п.** Исторические метрики не воспроизводятся вживую.

### 🔴 Безопасность
- **Дашборд на `0.0.0.0` без auth (верифицировано, `dashboard_server.py:2454`).** При этом
  `POST /api/settings` перезаписывает `config.yaml` (стопы/тейки/WT-пороги) с hot-reload, а
  `POST /api/trades/{id}/close` закрывает сделки. Нет auth, нет CSRF, `SameSite` не задан.
- **`ADMIN_ID` загружается, но нигде не используется** — нет разделения admin/user.
- **Нет валидации символов** в `_resolve_symbol` (спасает только отсутствие в `monitored_pairs`).
- *(Положительно: секреты в `.env`/`${ENV}`, `.gitignore` корректен, секретов в git нет; SQL —
  везде параметризованный.)*

### 🟠 Конкурентность и устойчивость
- **Утечки памяти.** `_last_signal` (`bot/core/bot.py:75`) и `analysis_cache`
  (`trading_intelligence.py:136`) растут без TTL/`maxsize`.
- **Race conditions.** `CircuitBreaker`/`OhlcvCache` (`api_engine.py:31–117`) без `asyncio.Lock`.
- **Нет авто-рестарта.** Необработанное исключение в `monitor_market()` → тихая остановка мониторинга.

### 🟠 Тестовое покрытие — перекошено
313 тестов покрывают детекторы, но **не покрыты:** `TradingIntelligence.analyze_symbol()`,
`api_engine.py`, `subscription_manager.py`, `dashboard_server.py`, конкурентность, БД-локи.
6 тестов `confluence_state_machine` сломаны.

### Сценарии деградации
- *Сеть* → `CircuitBreaker` спасает транспорт, но мониторинг может тихо встать; fallback регистрирует
  pivot-сделки **без AI** (`BOT_SIGNAL_MAP.md:305`).
- *Data deluge* → учащение SQLite-локов, перегрузка loop, ускорение утечек.
- *Изменение API BingX* → один клиент без типобезопасной прослойки → ломается весь сбор данных.
- *Рассинхрон часов хоста* → уже приводил к −9.74R.

## 4. Актуальность и нужность (Market-Product Fit)

**Боль реальная и массовая:** розничный трейдер тонет в шуме (600+ пар × 7 TF), бот автоматизирует
сканирование + даёт структурированную рекомендацию с симуляцией исходов.

**Критическое расхождение «обещание ↔ факт»:** README/CLAUDE.md рекламируют «**+22.1%, Sharpe 1.45**»
и «защиту от переобучения», тогда как реальные данные дают **WR 43.3%**, отрицательный `avg_R` по
части сигналов (`trend_signal` −0.50), а ML-валидация дефектна. Продукт **продаёт бэктест, который не
воспроизводится** → репутационный и **регуляторный** риск (торговые рекомендации + маркетинг
доходности без лицензии).

**Технологическая актуальность (2026–2030):**
- *В ногу:* ML-на-исходах, MTF-конфлюэнции, SMC, Strategy Pattern для A/B.
- *Догоняет:* REST-поллинг вместо WebSocket (ccxt.pro в ROADMAP, не внедрён); SQLite вместо
  Timescale/Postgres.
- *Отстаёт:* нет LLM-объяснимости, агентного исполнения, on-chain/sentiment-данных.

**Вывод:** концепция актуальна, реализация edge — нет.

## 5. Рыночная ниша и конкурентный анализ

**Ниша:** self-learning multi-timeframe signal & trade-simulation bot для розничного крипто-перп
трейдера (BingX). Барьер входа низкий, барьер на доверие — высокий (нужен верифицируемый трек-рекорд).

**Конкуренты:**
- *Платформы:* 3Commas, Cryptohopper, Coinrule, Bitsgap, Cornix (исполнение Telegram-сигналов).
- *Аналитика:* TradingView (alerts+Pine+соцслой), Coinglass/Velo.
- *Инди/OSS:* Freqtrade (зрелый), Jesse, тысячи приватных Telegram-ботов.

**Где проигрывает сейчас:** не исполняет сделки (только симуляция), уступает Freqtrade по
зрелости бэктеста/комьюнити, TradingView — по UX/экосистеме.

**Потенциальный Moat (если довести до ума):** замкнутый контур «реальная симуляция → MFE →
адаптивное обучение per-signal-type» + **прозрачный, честный, пер-сигнальный трек-рекорд из БД** в
нише, где всё держится на доверии и приукрашенных WR. **Сейчас moat подорван подгонкой ML.**

## 7. Сводный вердикт и дорожная карта оптимизации

### 🔴 HIGH PRIORITY — «не теряй деньги и не утекай» (1–2 недели)
1. **Закрыть дашборд:** bind на `127.0.0.1`, токен-auth + CSRF на все `POST`, задействовать
   `ADMIN_ID` (`dashboard_server.py:2454`).
2. **Sanity-guard на сделки:** алерт+форс-клоуз, если цена ушла >X% за SL при `OPEN`; источник
   времени — **биржевой**, не системные часы (защита от повтора #1910).
3. **SQLite-устойчивость:** `PRAGMA journal_mode=WAL` + `busy_timeout`; запись через
   `run_in_executor`.
4. **Починить установку:** `scikit-learn` в `requirements.txt`; healthcheck/restart в Docker.
5. **Авто-рестарт `monitor_market`** + устранить `except: pass` (`monitoring.py:101`).

### 🟠 MEDIUM PRIORITY — «честный edge» (2–6 недель)
6. Перестроить ML-валидацию на **`TimeSeriesSplit`**; если честный AUC ≈0.5 — не подмешивать ML в
   confidence.
7. Убрать **selection bias** в `RPredictor`; предсказывать реализованный R, а не MFE-идеал.
8. Оживить `regime` на инференсе; включить `TSL`/`EXPIRED` в обучение.
9. **Out-of-sample как обязательный gate** для нового сигнала; зафиксировать честный пер-сигнальный
   трек-рекорд (будущий moat + маркетинг без регуляторного риска).
10. TTL/`maxsize` для `_last_signal`/`analysis_cache`; `asyncio.Lock` на кеш/брейкер.
11. Тесты на `analyze_symbol`, `api_engine`, конкурентную запись в БД.

### 🔵 LONG-TERM — «платформа» (2–6 месяцев)
12. Удалить мёртвые `infrastructure/`/`presentation/`/`bot/main.py`; разнести `dashboard_server.py`.
13. PostgreSQL/TimescaleDB через ORM; WebSocket (ccxt.pro); контейнеризация воркеров.
14. Мульти-тенантность (per-tenant config/стратегии).
15. Определить продукт: «verified track-record SaaS» (рекомендуется) vs auto-execution/copy-trading.

## Резюме

Oko MTF Bot — **инженерно амбициозный, хорошо задокументированный self-learning signal-бот с
production-grade транспортным слоем и правильным контуром обучения**, подорванный тремя
фундаментальными проблемами: (1) ML-методология с selection bias и дефектной валидацией (бэктест 85%
→ реальные 34–48%); (2) отсутствие production-инфраструктуры (Windows-машина, SQLite, открытый
дашборд, отказ на −9.74R); (3) регуляторно-рискованная монетизация недоказанного edge. Ключевой шаг
лечения — заменить «красивый бэктест» на **честный, верифицируемый, пер-сигнальный трек-рекорд**:
он одновременно закрывает методологический долг, снимает регуляторный риск и превращается в moat.
