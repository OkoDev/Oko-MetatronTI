# ADR-003 — Шина Куба выходит из процесса бота: хаб `cube-hub`

- **Статус:** accepted 30.09.2026 (Егор: «хаб строить»); решения по открытым вопросам — раздел «Решения 30.09»
- **Дата:** 2026-09-30
- **Задача:** заводится после согласия · связано: BACKLOG N12 (шина), N15 (Сфера 1), N16 (один писатель на базу), карта созвездия 24.07 п. 1 «разбить монолит oko-bot»
- **Контекст-док:** [../METATRON-KERNEL.md](../METATRON-KERNEL.md), [ADR-001](ADR-001-external-services-via-port.md)

## Контекст

### Что есть сейчас (проверено по коду и живому боту 30.09)

Шина — два контура, **оба внутри процесса `oko-bot`**:

| Контур | Файл | Что делает |
|---|---|---|
| `PairContextBus` | `core/context/pair_context.py` | «Доска»: состояние пары `PairState` (95 полей), 27 типов `SphereEvent`, синхронный `publish`, журнал последних 200 событий только в памяти |
| `EventBus` | `core/context/event_bus.py` | Очередь переанализа: строковые события → Full CALL `analyze_symbol` (cooldown 30 мин, `shadow: false`) |

Живые замеры (`/api/cube/stats`, `/api/cube/events`, 30.09):
- 583 пары, 22 типа событий с подписчиками, 29 подписок;
- во время скана ~40 событий/с (200 событий за 5 с): `ohlcv_updated`, `regime_updated`, `wt_snap_updated`, `wt_verdict`, `smc_snap_updated`, `smc_verdict`, `pivot_snap_updated`. Это ~7 событий на пару за проход, то есть ~4 тыс. событий за цикл скана (оценка);
- состояние одной пары ≈ 8.3 КБ, полный снимок `snapshot_all` ≈ 1.1 МБ (отдаётся за 0.1 с).

Реальных потребителей мало (авто-память `bus_is_blackboard_not_mesh`). Работают NotificationDispatcher, нарратив Сферы 9 (синхронный), теневые «режим ↔ WT», счётчики SphereRegistry и `btc_regime` из `CROSS_MARKET`. Ещё три подписки — заглушки.

### Кто снаружи уже пытается говорить с шиной

Все внешние связи — обходные, и все зависят от того, жив ли бот:

| Процесс | Как связан | Проблема |
|---|---|---|
| `structure-term` (:8010) | опрашивает `GET :8000/api/cube/snapshot_all` раз в 60 с | бот лёг → старый снимок без пометки возраста |
| `oko-dash` (Next) | `GET /api/cube/stats`, `/api/cube/events` | то же |
| `dc-agent` (выключен) | `GET /api/cube/context/{sym}` | то же |
| вахты (`scripts/_alert.py`) | пишут `watch_state` в `oko_feed/watch.db` | бот узнаёт через `watch_bridge`: опрос раз в 300 с, только лог |
| `oko-sm-watch` | **сам регистрирует сделки `breakout`** через `TradeSimulator("subscriptions.db")` (7 сделок 25.07–12.08) | спутник пишет в таблицу бота в обход сигнального пути — нарушение N16 |
| любой скрипт | `POST /api/cube/event` → EventBus, белый список из 8 аналитических событий | вход только в EventBus, в доску не попадает |

Остальные ~20 процессов pm2 шину не видят вообще: контекст берут из SQLite и файлов.

### Почему это мешает

1. **Шина умирает вместе с ботом.** Бот перезапускается при каждой правке, а 29.09 он дважды вышел сам (04:17 и 17:41, починено). Каждый раз доска пустеет, а внешние клиенты получают старое или пустое.
2. **Монолит нельзя разбить без внешней шины.** Карта 24.07, шаг 1: сферу, вынесенную из бота, не к чему подключить. Сегодня есть только SQLite-файлы и HTTP самого бота.
3. **Спутники пишут в чужие таблицы**, потому что им некуда опубликовать. N16 навёл порядок с базами, но сигнал `breakout` так и идёт в `simulated_trades` напрямую.
4. **Опросы вместо событий.** `watch_bridge` узнаёт о смене вахты с опозданием до 5 минут, терминал — до 60 с.

## Что НЕ выносим (граница решения)

🔴 **Синхронная часть шины остаётся в процессе бота.** Урок 28.09: async-подписчик видит уже СЛЕДУЮЩЕЕ состояние пары, потому что скан успевает опубликовать ещё события. Поэтому решения, зависящие от состояния в момент события (нарратив Сферы 9, теневые «режим ↔ WT», будущие реакции выхода), считаются синхронно, внутри `publish`. Межпроцессная шина — это задержка от миллисекунд до секунды, и перенести туда такие решения нельзя.

Значит, «вынос» — это **второй уровень**, а не замена:

```
   процесс oko-bot                              pm2: cube-hub                     спутники
 ┌─────────────────────────┐   фоновая очередь  ┌──────────────────────┐  WS / HTTP  ┌─────────────┐
 │ PairContextBus (как есть)│ ─────────────────▶ │ доска: состояние пар │ ◀─────────▶ │ терминал,   │
 │ синхронные подписчики    │                    │ журнал фактов        │             │ вахты,      │
 │ EventBus (как есть)      │ ◀───────────────── │ поток подписки       │             │ oko-sm-watch│
 └─────────────────────────┘  входящий мост     └──────────────────────┘             │ сферы вне   │
                              (белый список)        один писатель                     │ бота        │
                                                    oko_feed/cube.db                  └─────────────┘
```

## Варианты

### A. Бот остаётся хабом, расширяем его HTTP (поток SSE + приём публикаций)
- ➕ Дёшево, почти всё уже есть (`/api/cube/*`).
- ➖ Не решает главного: шина по-прежнему умирает с ботом.
- ➖ Раздача потока подписчикам нагружает цикл событий бота. Раньше это уже ловили: флаг `dashboard.enabled=false` появился как раз ради изоляции нагрузки дашборда на цикл.
- **Отвергнуто** как конечное решение. Подходит только как временный шаг.

### B. Внешний брокер (NATS / Redis Streams)
- ➕ Проверенная технология: подписки, хранение, повторы.
- ➖ Новая инфраструктура на Windows. Redis официально не собирается под Windows (нужны Memurai или WSL). У NATS есть один exe, но его придётся изучать и сопровождать.
- ➖ Доску состояния (последнее значение по паре и полю) всё равно пишем сами поверх потока.
- **Не сейчас.** Остаётся открытым, если свой хаб упрётся в нагрузку. Клиентская библиотека (см. C) делает замену прозрачной.

### C. Свой хаб `cube-hub` (aiohttp, pm2) — **рекомендация**
- Отдельный процесс, **единственный писатель** `oko_feed/cube.db`. Тот же принцип, что у `market-store` и `sat_store`, и он уже работает.
- Держит **доску**: последнее значение (пара, поле) в памяти плюс снимок на диск, чтобы переживать свой рестарт.
- Держит **журнал фактов**: только редкие события-факты, append с ограниченным сроком хранения.
- Раздаёт `GET` снимков (пара / все пары / рынок) и **поток WebSocket** с подпиской на типы событий.
- Принимает публикации от производителей с **белым списком по производителю**.
- ➕ Стек проекта, никакой новой инфраструктуры. Шаблон «очередь → один писатель» уже проверен на Сфере 1.
- ➖ Свой код: примерно размер небольшого сервиса (точнее — после проектирования API). Сопровождать самим.

### D. Только файловые очереди (как `market_spool`), без хаба
- ➕ Предельно просто и надёжно для фактов.
- ➖ Нет живого состояния и снимков: каждый потребитель сам читает хвосты и сам собирает доску. Это ровно то дублирование, от которого лечили Сферу 1.
- **Отвергнуто** для шины. Годится как транспорт бот → хаб, если WebSocket окажется хрупким.

### E. `multiprocessing.Manager`
- **Отвергнуто:** на Windows хрупок (spawn, pickling), связывает процессы общим родителем. pm2-процессы так не живут.

## Решение

Вариант **C** плюс **клиентская библиотека-порт** в духе ADR-001:

- `core/context/cube_client.py`: `publish(event, symbol, data)`, `snapshot(symbol|None)`, `subscribe(types, handler)` —
  **те же три глагола, что в каноне «как слушать Куб»** (PRODUCE / PULL / PUSH, `docs/BUS_SUBSCRIBER_ROADMAP.md`,
  LISTENER-CANON 15.06). Это не новый контракт, а старый, доступный из любого процесса.
- Контракт данных — готовый каталог `core/context/bus_catalog.py` (`docs/BUS_CATALOG.md`); шаг 0 его расширяет, а не заводит новый.
- Производители и потребители зависят только от клиента, а не от транспорта. Смена C → B — правка одного модуля.
- **Публикация никогда не блокирует скан.** Из бота — через ограниченную очередь и фоновый поток. При переполнении старое выбрасывается, а счётчик потерь пишется в лог раз в N минут. Хаб лёг — бот торгует как сейчас.
- **Хаб лёг — клиенты не падают.** Снимок отдаётся с полем `age_sec`, а клиент решает сам, годится ли он.

### Два класса данных — разное хранение

| Класс | Примеры | Хранение | Почему |
|---|---|---|---|
| **Состояние** | `*_snap_updated`, `regime_updated`, `ohlcv_updated`, `tick_price`, `funding/oi_updated` | upsert (пара, поле) — только последнее значение | ~4 тыс. событий на цикл с полезной нагрузкой в килобайты. Журналировать их — гигабайты в сутки ни для кого |
| **Факт** | `signal_detected`, `position_opened/closed/dropped`, `trade_closed`, `tp1_hit`, `tsl_moved`, `cross_market`, `anomaly_detected`, смена вахты, внешний сигнал | append-журнал с `seq` производителя, срок хранения (предложение: 30 дней) | редкие; их нужно переиграть после рестарта подписчика |

### Правила контракта

1. **Одно поле — один владелец** (сфера-писатель), как «одна база — один писатель» в N16. Хаб отвергает запись поля не владельцем. Это защищает от двух версий правды.
2. **Каталог событий = контракт.** В `core/context/bus_catalog.py` у каждого события появляются класс (состояние/факт), владелец и признак «видно вне процесса». Тест проверяет, что каждый `publish` в коде есть в каталоге.
3. **Торговых команд через шину нет.** Внешний сигнал — это *факт* «спутник увидел сетап». Регистрирует и исполняет сделку только бот, по своим `signal_router.source_policies`. Источник без своей политики получает `default_policy.exchange_enabled: false` (config.yaml) — только SIM, как сейчас у EventBus.
4. **Входящий мост в бот** (подписчик хаба внутри бота) — один на всё, с белым списком. В него сливаются нынешние `POST /api/cube/event` и `watch_bridge`.
5. **Безопасность:** хаб слушает только `127.0.0.1`. Публикация — с токеном из файла `oko_feed/cube_hub.token` (хаб создаёт при первом старте; браузер файл прочитать не может). Запросы с заголовком `Origin` отвергаются: урок CSRF на :8010 (авто-память `terminal_localhost_csrf_live_orders`).
6. **Хаб ничего не считает.** Он хранит и раздаёт; любой признак считает сфера-владелец (инвариант METATRON-KERNEL №5 «один калькулятор на признак»). Хаб с логикой = второй монолит.
7. **EventBus наружу не выставляется.** Разбор ARCH-101 (30.09) показал: EventBus — очередь заданий «перепроанализируй пару», а не шина подписки; её вход снаружи (`POST /api/cube/event`) ведёт к `analyze_symbol` → `submit`. Внешние факты входят только через входящий мост с белым списком (шаг 4).

### Место в концепции Куба

- **Фрактальность** (ENCYCLOPEDIA → «Sub-кубы»): бот становится Sub-кубом «торговый контур» со своей внутренней синхронной шиной (`PairContextBus`), `cube-hub` — шиной главного Куба. Синхронная часть остаётся в боте не как уступка: так устроен любой Sub-куб.
- **Инвариант 4 «единый источник правды»:** правда поля — у сферы-владельца, хаб — реплика (правило 1).
- **METATRON-KERNEL §6–7:** хаб + клиент — первая реализация абстракции `SharedContextBus` через границу процессов (зерно этапа B `metatron-core`); вопрос транспорта из §7 решён для шины. В ядре два примитива: `AdvisorPort` (запрос-ответ) и клиент шины (публикация/подписка).

### Связь «все со всеми»

Ребро Куба = одна подписка потребителя на событие владельца. Через центр у каждой сферы одно подключение, и любое ребро
доступно, где бы ни жили сферы (13 сфер напрямую — 78 проводов, через центр — 13). Два моста в боте (наружу — факты и
состояние; внутрь — белый список) делают внешние события для сфер бота обычными `SphereEvent`. Хаб знает живые
подписки → граф рёбер измерим (сейчас лог «mesh-связность» считает провода, а не реакции). Mesh — возможность любого
ребра, а не все рёбра сразу: ребро заводится там, где у потребителя есть реакция, прошедшая замер (N12).
Поток кандидатов для потребителей уже есть: `POSITION_OPENED ∪ POSITION_DROPPED` роутера — все 19 путей регистрации.

## Порядок переноса (strangler, каждый шаг откатывается флагом)

Флаг `cube_hub.enabled` в `config.yaml` (плюс поле в `pydantic_config.OkoConfig` — иначе `extra=forbid` уронит валидацию). До шага 3 хаб только **добавляет**: бот работает как сейчас.

| Шаг | Что | Критерий готовности (замер, не рассуждение) |
|---|---|---|
| **0. Контракт** | Каталог: класс / владелец / внешняя видимость для 27 событий. API клиента на бумаге | Тест «каждый publish в каталоге» зелёный; таблица согласована с Егором |
| **1. Хаб в тени** | `cube-hub` в pm2; бот зеркалит события в хаб фоновой очередью | Снимок хаба = `snapshot_all` бота (расхождений по полям 0, кроме времени); задержка p95 < 2 с; потерь по `seq` 0; **длительность цикла скана не выросла** (сравнить до/после, как при переводе Сферы 1) |
| **2. Читатели** | Терминал, oko-dash, (dc-agent при включении) читают хаб, а не :8000 | Рестарт бота → терминал отдаёт снимок с `age_sec`, а не пусто или ошибку |
| **3. Первый внешний производитель** | `oko-sm-watch`: `breakout` публикуется фактом → бот регистрирует через входящий мост. Вахты `_alert.py` публикуют смену состояния | 0 записей спутников в `subscriptions.db` (закрывает хвост N16); смена вахты доходит до бота < 5 с вместо ≤ 300 с |
| **4. Входящий мост** | `POST /api/cube/event` + `watch_bridge` → один подписчик хаба в боте | Старые пути выключены флагом, поведение то же (сверка по логам за сутки) |
| **5. Сферы наружу — по одной** | Кандидаты — сферы без синхронных потребителей в скане (например, Сфера 5 Cross-Market отдельным процессом). **Exit Manager — последним** или никогда (торговый контур, синхронные решения) | Отдельное решение и замер на каждую сферу |

Шаги 0–2 не меняют торговлю вообще. Шаг 3 меняет путь регистрации одного редкого источника (SIM).

## Риски

| Риск | Чем закрыт |
|---|---|
| Хаб тормозит скан бота | Публикация через ограниченную очередь в фоновом потоке, выброс старого; критерий шага 1 — длительность цикла |
| Две версии состояния (бот и хаб) | Хаб — реплика; одно поле — один владелец; снимок сверяется на шаге 1 |
| Журнал раздувается | Журналируются только факты; состояние — upsert; срок хранения |
| Снова «database is locked» | Писатель `cube.db` один — хаб; остальные читают через API |
| Потеря событий при рестарте хаба | Факты с `seq` в журнале; подписчик после переподключения запрашивает «с seq N». Состояние восстанавливается из снимка на диске, а бот досылает его следующим проходом скана (~4 мин) |
| Внешний процесс шлёт мусор или торговые события | Белый список по производителю, токен, только localhost; торговых команд в контракте нет |
| Разрастание: 27 событий × 95 полей переносятся «на всякий случай» | Наружу — только то, у чего есть внешний потребитель (правило N12: событие без потребителя — шум) |
| Ещё один процесс pm2 на Windows | Шаблон перезапуска pm2 известен (авто-память `pm2_windows_restart_orphans`); клиенты переживают отсутствие хаба |

## Соответствие Кубу

- **Центральная сфера (Shared Context Bus)** перестаёт быть частью одного процесса и становится общей для всех сфер.
- **Новые рёбра:** спутники, которые сейчас «склад» (SQLite + опросы), становятся сферами с публикацией и подпиской. Первые рёбра — `oko-sm-watch → бот` (сигнал) и `вахты → бот` (режим).
- **Предусловие** для карты 24.07 п. 1 (разбить монолит) и для `metatron-core` (ADR-001): вынесенной сфере нужна шина, к которой можно подключиться.

## Честная оговорка о ценности

Это инфраструктура: **денег она не добавляет**. Эджа проект по-прежнему ищет (авто-память `anchor_dataset_company_no_revenue`). Выигрыш — надёжность (доска переживает рестарт бота), порядок (спутники не пишут в чужие таблицы) и возможность разбить монолит. Приоритет относительно поиска эджа — решение Егора.

## Решения 30.09

Егор: «хаб строить». По вопросам, где выбор не назван явно, приняты варианты из проекта (меняются одной строкой конфига / новым ADR):
1. **Вариант C** — свой хаб + клиент-порт (NATS остаётся запасным путём за клиентом).
2. **Журнал фактов — 30 дней** (`cube_hub.retention_days`).
3. **Сигналы спутников — только SIM**, пока источник не пройдёт форвард (правило 3 уже это обеспечивает).
4. **Начинаем сейчас:** шаги 0–1 торговлю не трогают.

## Проект шага 1 (хаб в тени)

**Бот → хаб (`core/context/cube_mirror.py`):**
- крючок в `PairContextBus.publish/update`: пара помечается «грязной»; событие класса «факт» сериализуется сразу и ставится в очередь;
- раз в `flush_sec` (1 с) задача в цикле событий берёт грязные пары **плюс N давно не отправленных** (круговой досыл):
  часть кода пишет поля пары напрямую (`state.btc_regime = …`, `set_watchlist`) мимо `publish/update`, круговой досыл
  ловит и это (полный круг по ~580 парам ≈ 30 с) и сам восстанавливает хаб после его рестарта;
- состояние пары = **все поля `PairState`** (надмножество `get_full_state()`, ключи те же — формат `/api/cube/context`
  не ломается). 🔴 `get_full_state` отдаёт выборку: фандинга, OI, волн в ней нет — это класс ошибки «API-дырка»
  (25.07 smc/pivot, 29.09 оборот); хаб её не повторяет;
- отправка — отдельный поток, ограниченная очередь, выброс старого со счётчиком; `seq` у каждой записи.

**Хаб (`scripts/cube_hub.py`, pm2 `cube-hub`, 127.0.0.1:8020):** `POST /publish` (пачка, токен) · `GET /state`,
`/state/{symbol}` (с `age_sec`) · `GET /facts?since=&types=` · `GET /ws?types=` (поток фактов) · `GET /stats`
(разрывы `seq`, задержка p50/p95, размеры). База `oko_feed/cube.db`: снимок состояний раз в 30 с, факты сразу, чистка
старше 30 дней. Флаг `cube_hub.enabled` (по умолчанию выключен).

**Классы событий (шаг 0, `bus_catalog.EVENT_CLASS`):** состояние — `ohlcv_updated`, `tick_price`, `wt_verdict`,
`wt_snap_updated`, `smc_verdict`, `smc_snap_updated`, `regime_updated`, `pivot_snap_updated`, `sphere_health`,
`funding_updated`, `oi_updated`, `cascade_updated`; факт — `signal_detected`, `anomaly_detected`, `volume_spike`,
`divergence_found`, `pivot_touch`, `cross_market`, `narrative_built`, `position_opened`, `position_dropped`, `tsl_moved`,
`tp1_hit`, `position_closed`, `trade_closed`, `ote_zone_set`; внутреннее (наружу не идёт) — `recommendation_built`
(несёт объект рекомендации).

## Последствия

**Плюсы:** доска переживает рестарт бота; события вместо опросов; спутники перестают писать в базу бота; появляется путь для разбиения монолита; транспорт заменяем.

**Минусы / плата:** ещё один процесс и свой код хаба; две копии состояния (бот и реплика), которые надо держать согласованными; задержка межпроцессной доставки (синхронные решения остаются в боте — это граница, а не недостаток).
