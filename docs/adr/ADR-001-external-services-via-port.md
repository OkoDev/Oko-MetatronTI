# ADR-001 — Внешние сервисы подключаются через Port, а не встраиваются

- **Статус:** accepted
- **Дата:** 2026-05-31
- **Задача:** ARCH-125
- **Контекст-док:** [../METATRON-KERNEL.md](../METATRON-KERNEL.md)

## Контекст

Архитектура «Куб Метатрона» имеет фрактальные Sub-кубы ([CUBE_SUBCUBES.md](../CUBE_SUBCUBES.md)), но все они **вкомпилированы** в процесс бота (`SubCube.compute_and_publish()` синхронно в `scan_loop`). Это верно для быстрой детерминированной доменной логики (SMC, Pivot, WT).

Появился класс сервисов с другими свойствами: **LLM-рой** (и в будущем внешний ML, чужие аналитические сервисы). У них:
- недетерминизм и галлюцинации,
- latency 1-3с (несовместимо с торговым контуром 24/7),
- ценность переиспользования в других проектах,
- собственный темп эволюции и деплоя.

Сам рой при опросе (6/7 голосов, [[memory/last_team_discussion]]) выбрал быть **независимым сервисом**, а не встроенной сферой — по аргументам риск-изоляции, слабой связности и переиспользования.

## Решение

Куб **подключает** такие сервисы через типизированный **Port** (паттерн Hexagonal / Ports & Adapters), а не встраивает их:

- Куб определяет контракт `AdvisorPort` (`consult(AdvisoryRequest) -> AdvisoryVerdict | None`, `health()`), версионируемый (`schema_version`).
- Внешний сервис реализует **Adapter** под этот контракт.
- На стороне Куба — `AdvisorConnector` с timeout + circuit breaker; падение/таймаут советника → `None` → Куб работает по базовой логике.
- Результат ложится в Shared Context Bus как `advisor_snap` — **опциональный** сигнал. Ни одна execute-функция не требует его наличия.

Полная спецификация контракта — [METATRON-KERNEL.md §2](../METATRON-KERNEL.md).

## Альтернативы (отвергнуты)

- **A. Встроить рой как 13-ю сферу** (синхронный Sub-куб). Отвергнуто: вносит недетерминированную точку отказа в live-контур, жёсткая связь убивает переиспользование, обновление роя требует рестарта бота. (Позиция Mistral — единственный голос «за», но даже он оговорил «если нет других проектов».)
- **B. Прямые вызовы LLM из execute-функций.** Отвергнуто: конвейер вместо mesh, нарушает инвариант Куба, дублирует логику вызова в каждой точке.

## Последствия

**Плюсы:**
- Риск-изоляция: сбой советника не трогает торговлю.
- Слабая связность: рой переиспользуется в любом проекте, бот — лишь первый клиент.
- Независимый деплой и эволюция (team-update внутри сервиса).
- Куб становится «готов к подключению» сторонних аналитиков без изменения ядра.

**Минусы / плата:**
- Сетевой/процессный boundary → latency и нужда в transport (REST/gRPC/stdio — решается позже).
- Нужна сериализация `snapshot` (проекция `PairFullState`).
- Дополнительный слой (Connector + breaker) на стороне Куба.

**Зависимости:** контракт фиксируется ПЕРВЫМ — от него зависят и извлечение роя в `swarm-service`, и реализация порта в `scan_loop`. Эти шаги — отдельные задачи после ARCH-125.
