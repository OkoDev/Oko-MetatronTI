## TL;DR
**BingXClient НЕ гнилой.** ~85% = либо выстраданные фиксы (кодируют реальное поведение биржи и прошлые инциденты), либо тонкий HTTP-плюминг. Реальный запах — **дублирование** (3× retry timestamp 109400, 2× парсинг ban) и **отсутствие** пары методов (set_leverage/set_margin_mode standalone). **Источник денежных дыр был НЕ здесь** — он в оркестрации (`position_sync`/`exec_ws_integration`/`trade_router`), которую эпик и сносит. → План A подтверждён: клиент обернуть, дубли консолидировать ВНУТРИ адаптера как тех-уборку (не на критическом пути).

## 🟢 Выстраданные фиксы — НЕ трогать (переписать = вернуть класс багов)

1. **GlobalRateLimiter + `_maybe_set_ban`** (`:340-359`, ARCH-96 Ф1) — при 100410/109429 глобально паузит ВСЕ клиенты/субаккаунты. Лечит каскад rate-limit бана. Кодирует реальное поведение IP-бюджета BingX.
2. **`sync_time` offset + throttle + force-resync на 109400** (`:176-246`, DEV-145/D-071) — timestamp invalid каскад. Throttle (60s/30s) разрывает порочный круг «order timeout → force sync → timeout → retry». Без него — лавина 109400→109429 (бан за 20+ ошибок).
3. **Precision cache + quantize** (`:248-306`) — биржа отвергает qty/price неверной точности. Кэш контрактов = один запрос, потом floor/round локально.
4. **`get_positions` бросает RuntimeError, НЕ возвращает `[]`** (`:533-544`) — прямой урок инцидента 2026-04-07: пустой список из-за API-сбоя трактовался как «позиций нет» → массовое ложное закрытие tracked-сделок. Это **тот же класс**, что эпик чинит на уровне выше (fail-closed).
5. **`close_position_market` hedge-логика** (`:668-718`, КОРЕНЬ 101205 + OPS-06) — retry без reduceOnly на 109400/101205 (hedge не видит сторону) + positionId + one-click fallback. Каждая ветка = конкретный код ошибки BingX в hedge-mode. Снести = вернуть «No position to close» и orphan-семью.
6. **Dual-signing `place_bracket_order`/`post_raw`** (`:572-610`, `:425-443`) — HMAC по raw_qs, URL по url-encoded JSON. BingX-специфика подписи вложенных JSON (stopLoss/takeProfit объекты). Не «красиво», но единственно работающее.
7. **keep-alive `ClientSession` + `_route`** (`:117-167`) — PERF (RTT 400→250) + изоляция REST в торговый loop от scan-starvation.

→ Это и есть «биржевая реальность», ради которой адаптер ОБОРАЧИВАЕТ, а не переписывает. Переписывание = пере-открытие этих инцидентов.

## 🟡 Реальный запах — кандидаты на консолидацию (НЕ источник дыр, делать ВНУТРИ адаптера/позже)

1. **Тройной дубль retry timestamp 109400** — идентичный блок в `_get_impl` (`:380-389`), `_post_impl` (`:412-421`), `_delete_impl` (`:463-472`). Просится в один декоратор/обёртку `_request_with_resync`. Это буквально та «лоскутность», на которую жалуется эпик — но локальная (HTTP-слой), не денежная.
2. **Дубль ban-парсинга в `get_balance`** (`:486-516`) — своя обработка 100410/109429, хотя `_maybe_set_ban` (`:390`,`:422`,`:473`) уже ставит глобал-бан в каждом `_impl`. Избыточно — `get_balance` мог бы полагаться на общий механизм.
3. **`get_balance` парсит 4 ключа баланса** (`:519`) — defensive, но запах «не знаем точное поле».

→ Уборка этих дублей = отдельная низкорисковая задача (можно прямо в `BingXAdapter`, скрыв 3 retry за одной обёрткой). НЕ блокер корня, НЕ на критическом пути closing-логики.

## 🔴 Чего НЕ хватает (gaps — важно для перестройки)

1. **Нет standalone `set_leverage`** — плечо ставится ВНУТРИ `place_bracket_order` (`:586-588`). `BingXAdapter.set_leverage` честно отметил best-effort. Для отдельного управления плечом (re-leverage без переоткрытия) — добавить метод.
2. **Нет `set_margin_mode`/marginType** — подтверждает: бот НЕ управляет margin-mode (memory `orphan_root_dbexch_desync` / margin-enforce кирпич). `cross`-дрейф acc2 (−$322) молчит. Нужен `POST /trade/marginType` → `BingXAdapter.set_margin_mode` (enforce-кирпич).
3. **Нет `user/income` REST** (funding/commission/realized леджер) — НО WS `o.rp`/`o.n`/`a.m=FUNDING_FEE` заменяет (ExecutionLedger DS). Для бэкфилла истории мог бы пригодиться REST income, но не критично.

## Объём (грубо, по прочитанному)
- **≈60%** (450 строк) — выстраданные фиксы + HTTP-плюминг → обернуть как есть.
- **≈15%** (110 строк) — дублирование (109400×3, ban×2) → консолидировать в адаптере (тех-уборка).
- **≈25%** — dataclasses + factory + тонкие высокоуровневые методы → естественно мигрируют под `ExchangeAdapter`.

## Вердикт
Клиент — рабочий слой, обросший НУЖНЫМИ фиксами (биржевая реальность) + локальным дублированием HTTP-retry. **Денежные дыры эпика рождались НЕ в нём**, а в оркестрации над ним. Поэтому: **план A верен** — оборачиваем `BingXClient`, сносим больную оркестрацию. Консолидацию дублей 109400/ban — отдельной тех-уборкой внутри `BingXAdapter`, когда дойдём; на критический путь корня НЕ ставим. Полноценный ccxt-rewrite — не оправдан (риск > польза, не корень).
