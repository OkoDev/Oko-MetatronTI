**Что радар знает про волны (26.09.2026).** У него СВОЙ счёт, не связанный с ядром OKO-SM:
`_wave_leg()` в `scripts/oi_fast_poller.py` — ZigZag на 15m за 24 ч по данным **Binance**
(dev адаптивный 2.5× средний |ret|, кламп 1–3%), считает, какая по счёту импульсная нога идёт
от базы; волна ≈ 2n−1. Гейт 14.07 `pump_min_wave_leg: 3` — «pump-разворот только после выдоха».
Про ядро волн (`mark_impulse`, пятёрка 4h = [[wave_fifth_is_master_context]]) и про ноги из шины
(`wave_leg_up/dn` от `wave_analyst`) радар не знает ВООБЩЕ — это отдельная возможность.

**Гейт не работал НИ РАЗУ за 2.5 месяца.** `_fetch_new_orders` (radar_armed_loop) не выбирал
колонку `wave_leg` из `radar_orders` → `o.get("wave_leg")` всегда None → условие `_wl is not None`
ложно → проходили все. Улики: **0 отсеиваний по wave_leg из 41 924 SKIPPED**; 119 заявок с leg<3
ушли в бой уже после введения гейта, последние — в день находки. Фикс: колонка добавлена в оба
варианта SELECT (коммит `069ac06`).

**Цена дыры** (переигрыш 30 дней на публичных klines, 58 сделок): leg≥3 даёт **+2.20%/сд**,
leg<3 — **−1.93%/сд**. Лучшая корзина leg=3: +4.71, WR 56%, медиана +4.03 (единственная корзина
радара с положительной медианой).

**Why:** тот же класс, что молчаливый пропуск waves_long и [[bug_gate_lives_in_two_places]] —
фильтр написан, но данные до него не доходят, и он молчит, потому что нечему сработать.
Ни лог, ни статистика такого не покажут: в журнале просто нет строк с этой причиной.

**How to apply:** после внедрения любого гейта проверять его СЛЕДЫ в журнале — сколько раз
сработал. Ноль срабатываний за период = гейт мёртв, пока не доказано обратное. Для радара:
`select count(*) from radar_orders where note like '%<причина>%'`.

## 🔴 ГРЕЙД РАДАРА — ЭТО НЕ КАЧЕСТВО, А ТИП СЕТАПА (27.09, Егор: «почему не берёт C?!»)

Grade у фейда ставится по OI: **A** = OI падает («стопы, не загрузка») + объём ×5, **B** = OI падает,
**C** = OI растёт ЛИБО сработало правило «цикл загрузка→выстрел» (был сигнал в ту же сторону →
«разворот преждевременен»). Второе даёт 603 C из 695.

Но на деле грейд почти совпал с ТИПОМ сетапа, а платит только один тип:

| тип | n | средн | Δr | RSI | где сидит |
|---|---|---|---|---|---|
| **ФЕЙД ПАМПА** (шорт вершины) | 555 | **+0.27** | **+0.45** | 80 | 435 из них — grade **C** |
| ФЕЙД дампа (лонг дна) | 319 | −0.16 | −0.19 | 20 | A/B |
| ПРОДОЛЖЕНИЕ дампа (шорт вниз) | 232 | **−0.64** | **−0.67** | 29 | 175 в B, 57 в A, **0 в C** |

**Фильтр `pump_grades: [A, B]` работает как анти-фильтр:** выбрасывает лучший класс (фейд пампа
почти целиком помечен C) и оставляет худший (продолжение дампа — только в A/B).
Внутри самого фейда пампа грейд не ранжирует: A Δr −0.01 · B +0.11 · C +0.55.

Варианты фильтра на одних данных: сейчас A/B → Δr −0.30 (сумма −180) · разрешить C → +0.03 (−49) ·
**только фейд пампа, любой grade → Δr +0.45, сумма +149, медиана +0.26, WR 53%** ·
фейд пампа + A/B → +0.08 (грейд внутри типа только мешает).

**Честно:** даже лучший класс ХРУПОК — без верхних 10% сделок сумма −244; охват 112 монет из 210;
июль почти ноль (Δr +0.06), август +0.66, сентябрь +0.41. Это «менее плохой класс», а не эдж.
