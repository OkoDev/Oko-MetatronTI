# 🔴 УЗКОЕ МЕСТО СКАНА — КАНАЛ (доказано 02.09.2026)

## Что мерили

Прокси включены (3 ISP Сингапура, разные /24). Профиль поднимали поэтапно,
на каждом шаге меряли циклы и latency.

| профиль | циклы | latency медиана | p90 |
|---|---|---|---|
| direct (без прокси) | 756–832, выброс **3341** | 2469–14086 мс | — |
| прокси 15/30/40 | 314 · 316 · **318** · 437 · 481 → **медиана 318** | **1828 мс** | 4453 |
| прокси 25/50/60 | **652** (холодный) · **685** | **3250 мс** | 8110 |

```
параллелизм  ×1.67  (scan_semaphore 15 → 25)
latency      ×1.78  (1828 → 3250 мс)
пропускная   ×0.94  — УПАЛА
```

## 🔑 Вывод: насыщено ОБЩЕЕ узкое место, и это канал

Классическое переполнение: добавление параллелизма удлиняет очередь, не увеличивая
поток. Ключевая деталь — **latency росла у ВСЕХ ТРЁХ прокси одновременно**.
Будь дело в per-IP лимите биржи, три разных адреса так вести себя не могли бы.
Общее у них одно: домашний канал Егора.

Совпадает с инцидентом 16.07 (коммит `c757b48`): «30 коннектов = сатурация линии,
таймауты BingX, CancelledError на load_markets».

🪤 **Ловушка замера, стоившая половины проб:** каждый рестарт бота обнуляет кэш OHLCV,
и ПЕРВЫЙ цикл после него идёт 650–740 с независимо от настроек. За сессию было 7
рестартов — половина замеров мерила не конфигурацию, а последствия вмешательства.
Сравнивать профили можно ТОЛЬКО на прогретом кэше, пропуская первый цикл.

## Практические следствия

🔴 **Покупка ещё прокси скан НЕ ускорит.** Три адреса уже упираются в канал.
Остаются два рычага:
1. **Сократить число запросов** — WS на 3m/5m даёт −63% REST ([[scan_cycle_formula_latency]])
2. **Сменить канал или вынести бота на VPS** — тогда прокси заработают в полную силу

## Что прокси всё-таки дали (не обесценивать)

| | до | после |
|---|---|---|
| медиана цикла | 832 с | **318 с** (в 2.6 раза) |
| максимум | **3341 с** | 687 с |
| выбросы latency >8 с | 11–75% | **0%** |

Главное — исчезли многотысячные выбросы, которые и создавали циклы по 3341 с.
Это результат распределения накопительного троттлинга по трём IP
([[bingx_soft_throttle_by_ip]]).

## Рабочий профиль (не поднимать без смены канала)

`config.yaml → proxy_pool.overrides`: `api_rps 40 · scan_semaphore 15 · api_semaphore 30`
`rps_per_proxy 35` — 3×35=105 выше глобальных 40, не мешает.

🔑 Области действия (частая путаница): `api_semaphore_size` и `api_rps` — **на весь
пул** (один Semaphore, глобальный singleton). `rps_per_proxy` — **на каждый адрес**.

## Попутно исправлено

**Бан 100410 больше не тормозит весь пул.** Было: любой бан → `set_ban()` →
глобальная пауза, встают все три адреса. Стало: `ProxyPool.quarantine(url, sec)`
выводит только тот адрес, через который шёл запрос (бан выдаётся ПО IP —
market-data идёт без ключа). Сработало в бою: «выведен на 30s; живых: 2/3».

**Пароль прокси утекал в логи** — `logger.warning` печатал полный url с кредами,
`stats()` отдавал его наружу. Код от 09.06, всплыло при первом боевом включении.
Добавлен `_mask()`, старые вхождения вычищены. Машина локальная, потому не критично.
