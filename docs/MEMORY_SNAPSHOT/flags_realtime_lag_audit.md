# 🔬 АУДИТ ЛАГА ФЛАГОВ: виден ли флаг на своём баре (13.08.2026)

Задача от Егора после находки [[bug_fvg_flag_shifted_two_bars]]: «проверить у OB и Elliott»,
«проверить наборы ote_nested на правильность детекции импульса».

## 🔑 Метод — почему прошлый тест причинности не годился

Прошлый тест (`combinator_flags_causality.py`) спрашивал: **переписывается ли флаг задним
числом?** На FVG он дал 0.010% и ПРОПУСТИЛ баг смещения на 2 бара. Причина: флаг на баре
i−2 не переписывается — он стабильно ставится на i−2, как только в данных появляется бар i.
Расхождение видно только у самого края обрезки.

Правильный вопрос: **в момент бара b знает ли детектор, что на b есть флаг?**
```
compute_flags(df[:b+1]).iloc[-1][flag]  ==  compute_flags(df).iloc[b][flag]
```
Плюс замер ЛАГА: через сколько баров после b флаг становится виден.
Скрипт: `scripts/flags_realtime_visibility.py` (`--only`, `--max-lag`).

**Этот тест обязателен для любого нового детектора.** Старый тест на переписывание
систематическое смещение не ловит.

## 🔴🔴 Главное следствие: ote_nested стоит на флаге с лагом >20 баров

OTE-зона строится по ноге импульса, нога — по swing-структуре (`lh`/`ll`), а та
подтверждается окном вперёд. Значит **детекция импульса в OTE непричинна**: зона,
приписанная бару b, реально известна только через 20+ баров.

Это количественно объясняет разрыв SIM↔биржа у `4h_1h_pull` (единственный `enabled`
сетап ote_setups.yaml):

| 4h_1h_pull | n | WR | PF | %/сд net | безтоп10% |
|---|---|---|---|---|---|
| вся база (SIM+биржа) | 1262 | 51.6% | 1.35 | +0.295% | −367.8 |
| **только реальная биржа** | **284** | **27.1%** | **0.43** | **−0.666%** | −293.3 |
| только SIM | ~978 | ~80% | ~21 | ~+1.7% | — |

**На бирже сетап убыточен.** SIM показывает WR 80% против 27% на бирже — это не просадка
эджа, это другой прибор. Подтверждает [[exec_sim_split_epic]]: SIM=research, VST/биржа=истина.

⚠️ Ловушка выборки, в которую я попал по пути: `ORDER BY id DESC LIMIT 60000` отрезал
SL-сделки 4h_1h_pull, и разрез показал «TP 573, TSL 144, EXPIRED 121, SL — НОЛЬ» и PF 10.27.
**Сетап без единого убытка = признак кривой выборки, а не эджа.** Всегда проверять
распределение статусов перед вердиктом.

## ✅ ПОЧИНЕНО 13.08.2026 — OTE-зона (команда Егора «проверить детекцию импульса»)

Корень в `core/calculators/swing_bridge.py::etl_ote_premium` — грубее, чем у FVG:
```python
choch_ote = find_choch_ote(breaks, df)   # ОДНА зона от ПОСЛЕДНЕГО CHoCH всей истории
for i in range(n):                       # и красит ВСЕ бары задним числом
    if zone[0] <= close[i] <= zone[1]: ote_long[i] = True
```
`find_choch_ote` берёт `chochs[-1]`. Пока CHoCH не случился — зоны нет; как только случился —
она ретроактивно подсвечивает всю прошлую историю. Это класс-2 (скан всего df).
Ирония: в ТОЙ ЖЕ функции двадцатью строками выше premium/discount сделаны ПРАВИЛЬНО —
rolling со swing, подтверждённым к бару (`_sw[_si][0] + _LEN <= i`).

**Фикс:** зона действует только с бара своего CHoCH до следующего; `find_choch_ote`
переиспользуется на префиксе (`breaks[:j+1]`, `df.iloc[:bi+1]`) — вызовов = число CHoCH,
не число баров, формула не дублируется (ARCH-118 «один калькулятор» соблюдён).

Проверка: `ote_long_1h` — **лаг 0, чист**. Частота флага стала точечной:
`ote_long` 1.51% баров, `ote_short` 0.87% (раньше зона была размазана по истории).
Регрессий нет: 65 passed (SMC + arch104_integration + новые контрактные тесты FVG).

⚠️ Следствие: **все прошлые замеры ote_nested недействительны** — они мерили
ретроактивно раскрашенную историю. Набор `config/ote_setups.yaml` (18 сетапов,
avgR 0.19–0.96, wr 66–81%) требует полного перемера.
