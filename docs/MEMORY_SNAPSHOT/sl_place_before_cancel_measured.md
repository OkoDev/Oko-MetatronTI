**Замер (форсированная проверка на живой VST-позиции #60626 JUP SHORT, Егор: «форсировать»).**
Сдвинул стоп на 0.2% в сторону прибыли — ровно то, что делает трейлинг:

```
ДО:    1 стоп  [2105719206149971969]
+2.6s  2 стопа [новый, старый]   ← BingX ПРИНЯЛ второй при живом первом
+5.6s  2 стопа
+6.6s  1 стоп  [новый]
update_sl вернул новый id за 6.1 с
```

🔑 **Главное: конфликта стопов НЕТ.** Биржа спокойно держит два STOP-ордера на одной позиции
(hedge mode, positionSide). Позиция ни мгновения не была без защиты. Бот после подмены ничего
не чинил — `repair_missing_sl` не сработал, БД и биржа согласованы.

**Из чего складываются 6 секунд:** постановка нового → пост-проверка `place_sl_order`
(sleep 3 с + повторный fetch «ордер реально есть») → снятие старых. Окно с двумя стопами ~4 с
(дольше 3 с из-за сетевых задержек).

🔴 **Остаточный риск, названный честно:** в эти ~4 с сработать может СТАРЫЙ стоп (для SHORT он
выше нового, для LONG ниже) — тогда выход по худшей цене. Прежний порядок в том же сценарии
оставлял позицию голой, что хуже.

**Почему правка вообще понадобилась дважды:** первая версия (`45ddec9`) НЕ работала — внутри
`place_sl_order` жил свой анти-дубликат (Bug fix 20.04), снимавший старые SL перед постановкой,
и окно просто переезжало внутрь вызова. Вскрылось на вопросе Егора про конфликт стопов; лечение —
параметр `keep_existing` (`12594e8`). Юнит-тесты это пропустили, потому что мокали
`place_sl_order` целиком: **мок скрывает внутренности, которые и есть дефект**.

**How to apply:** инструмент замера — `scratchpad/force_tsl_check.py` (двигает стоп и параллельно
опрашивает биржу, печатая хронологию). Тем же приёмом можно ловить любые гонки ордеров.
