`core/calculators/combinator_core.py` `_calc_divergence` (используется во ВСЕХ `rsi_div_*` флагах через `compute_flags`) — внутренний helper `_last_confirmed_pivot(pivs, i)` пересканировал список пивотов **с начала** на каждом баре `i` цикла `for i in range(prd+6, n)`. Поскольку `i` растёт монотонно, это O(n²) суммарно — на 15m (24k баров) терпимо, на 5m (148k баров) — 89.6s/234M вызовов genexpr, доминирующая часть `compute_flags` (241s из 307s профиля BTC/USDT 4h→5m).

Исправлено (24.06, после "проверяй 5м" Егора): курсор `pl_cur/ph_cur`, продвигается только вперёд (since `i` монотонен) — O(n) суммарно, тот же результат (один проход вместо пересканирования). **Эквивалентность верифицирована** прогоном старой/новой версии на 3 паре/ТФ (BTC 15m, ETH 5m, 1000BONK 15m) — массивы bull_reg/bear_reg/bull_hid/bear_hid побайтово идентичны.

**Why:** блокировало бэктест OKO-OTE confs≥3 на 5m break_tf (164s/символ → 100 пар = ~4.5ч). После фикса 84.9s/символ (BTC) — ~2x.

**How to apply:** если ещё где-то в проекте всплывает O(n²)-подобная медленность на больших df (5m/3m, много баров) — искать паттерн "пересканировать список/массив с начала в цикле по монотонно растущему i" → курсор/two-pointer. См. также [[bug_fvg_overlap_held_lookahead]] — вторая, НЕ исправленная перф-дыра в той же области (detect_fvg_overlap), которую решили не трогать (риск для live-семантики).
