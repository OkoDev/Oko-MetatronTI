# ⏰ ВРЕМЯ В БД: UTC без таймзоны против локального

**Инцидент 01.09.2026.** Я час чинил «остановившуюся запись `signal_drops`»: строил гипотезы
(насыщенный пул потоков, cross-loop дедлок `asyncio.Lock`), правил код, перезапускал бота.
Запись НЕ ЛОМАЛАСЬ НИКОГДА — по часам того дня: 165 · 41 · 450 · 445 · 361 · 173 записей.

Корень ошибки: `dropped_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP` — SQLite пишет **UTC без
суффикса таймзоны**. Я сравнивал с ЛОКАЛЬНЫМ временем (МСК = UTC+3), то есть запросы
`WHERE dropped_at >= '15:14'` смотрели **на три часа в будущее** и возвращали ноль.

## Форматы времени в этой БД РАЗНЫЕ — проверять перед каждым сравнением
| поле | формат | пример |
|---|---|---|
| `signal_drops.dropped_at` | **UTC, БЕЗ tz** (`CURRENT_TIMESTAMP`) | `2026-09-01 12:31:41` |
| `simulated_trades.created_at` | ISO **с** tz | `2026-09-01T12:18:05.050178+00:00` |
| `simulated_trades.closed_at` | ISO **с** tz | `2026-09-01T12:02:10.110105+00:00` |
| логи `logs/crypto_bot.log` | **локальное** время (МСК) | `2026-09-01 15:31:41` |

⚠️ В одном отчёте легко смешать лог (МСК) и БД (UTC) — расхождение ровно 3 часа выглядит
как «данные отстают» или «поток прекратился».

## Правило
Сравнивать время в SQL **только средствами SQLite**: `datetime('now','-15 minutes')` —
`now` там уже UTC, обе стороны в одной шкале. Для питоновских сравнений брать
`datetime.now(timezone.utc)`, а не `datetime.now()`.

## 🔴🔴 06.10: ЭТОГО ПРАВИЛА НЕДОСТАТОЧНО — РАЗДЕЛИТЕЛЬ «T» ЛОМАЕТ СРАВНЕНИЕ

Я выполнил правило выше (`WHERE created_at >= datetime('now','-12 minute')`) — и получил
**полностью ложный результат**: в «последние 12 минут» попали записи от 11:05 того же дня.

Корень: SQLite сравнивает эти значения как СТРОКИ, а форматы разные —
`created_at` = `2026-10-06T16:20:43+00:00` (разделитель **`T`**, 0x54),
`datetime('now')` = `2026-10-06 16:57:33` (разделитель **пробел**, 0x20).
`'T' > ' '`, поэтому **любая** запись с `T` в ту же дату проходит фильтр.

**Рабочая форма** (нормализовать разделитель и срезать таймзону):
```sql
WHERE substr(replace(created_at, 'T', ' '), 1, 19) >= datetime('now', '-12 minute')
```

🔑 **Цена ошибки зависит от окна:** на 14-дневном окне искажение почти нулевое
(все записи внутри окна одного формата — числа сошлись 482 против 483), а на коротком
окне результат переворачивается полностью. То есть ошибка НЕ видна на больших выборках
и бьёт именно там, где проверяешь «сработало ли только что».

В `simulated_trades` живут ОБА формата: 55 909 записей с `T` (с 23.03.2026) и
3 093 с пробелом (до 23.03.2026) — проверено 06.10.

🔑 Симптом «ровно ноль записей за период, хотя механизм жив» = первым делом проверить шкалу
времени, а уже потом искать баг в коде. Дешёвая проверка: `select max(dropped_at)` рядом с
`select CURRENT_TIMESTAMP` — если разница кратна часовому смещению, дело в шкале.
