# 🔴🔴 «ПОЗИЦИИ БЕЗ БИРЖЕВОГО СТОПА» — ЭТО БЫЛ ДЕФЕКТ УЧЁТА (28.08.2026)

Задача FIX-STOPS стояла первым пунктом слоя 0 с формулировкой «22% позиций
открываются БЕЗ биржевого стопа, 27 пробоев −1R за август, худший −15R (MOVR).
Пока не починено — любая математика PF фикция». Разбор показал: **стоп был,
сработал, а запись в БД говорит обратное.**

## Порядок проверок был обратным

`core/exchange/tsl_updater.py` → `repair_missing_sl`. Было:

    live_sl_oid = get_sl_order_id()        # на бирже SL нет
    if db_sl_oid: set_exchange_sl_order_id(trade_id, "")   # ← ЧИСТКА
    real_qty = get_position_qty()          # ← ПРОВЕРКА ПОЗИЦИИ ПОЗЖЕ
    if not real_qty: continue

Стоп сработал → ордера на бирже нет → позиции тоже нет, но запись ещё `OPEN`
(окно до 60 с между исполнением и закрытием записи) → id затирается пустой строкой.
Сделка НАВСЕГДА остаётся «открытой без биржевого стопа».

**Стало:** сначала `get_position_qty`, и `""` пишется ТОЛЬКО когда позиция ЖИВА,
а стопа на ней действительно нет.

Позиция была защищена всё время. В БД — «без стопа».

## Число −15R тоже фикция: CR-DELTA делит на устаревший qty

Лимитка на 389.9879 контрактов заливалась **тремя порциями** (14.32 → 157.42 →
389.99, с 02:51 до 06:17). WS шлёт `TRADE_UPDATE X:"FILLED"` на КАЖДУЮ порцию,
поле `q` — размер ЗАЯВКИ, а не исполненного → бот считал позицию размером 14.32.
При закрытии `Δcr = −10.18 USDT` поделили на устаревшее количество:

| | записано в БД | по данным биржи |
|---|---|---|
| цена выхода | 1.4138094 | `ap` = **0.7286** |
| результат | **−101.1%** / **−15.0R** | ≈ −3.7% / ≈ **−1.2R** |
| деньги | — | **−10.24 USDT** на депо 455 (−2.2%) |

## Разрез, без которого вывод переворачивается

| срез | доля «без sl_oid» |
|---|---|
| все строки с `exchange_order_id` (август) | 39.9% |
| 🔴 **исключить `CANCELLED`/`PENDING_ENTRY`** (позиции не было вовсе) | **23.2%** |

Метрика «22%» считалась по второму срезу и арифметически верна — но означает
не «позиция без защиты», а «id стёрт после срабатывания». Из 24 пробоев хуже
−1.05R без `sl_oid` у **23 из 24** выход лежит в 1.05–2.3 стопа — обычное
проскальзывание, а не бесконтрольный полёт. Выброс ровно один — MOVR, и он артефакт.

## 🔑 ВТОРОЙ КОРЕНЬ: защита от pa-глюка ломалась о ЛИМИТНЫЙ вход

`core/execution/position_store.py::apply_position`. Защита от глюка BingX
(LAB 13.07: `pa 52.2→522.0` ×10 при неизменном `ep`) стояла на посылке
**«реальный добор сдвинул бы среднюю цену входа»**. Для лимитки посылка ЛОЖНА:
порции исполняются по ОДНОЙ цене, `ep` не двигается вовсе → защита резала
ЗАКОННЫЙ рост позиции. Тот же класс, что [[bug_live_orders_bridge_broken_by_limit]]:
механизм писан под MARKET-вход и ломается о лимитный.

Различитель — размер НАШЕЙ заявки: BingX **не шлёт `z`** (накопленный филл),
только `q`, и он известен с ПЕРВОГО fill-события. Рост в пределах заявки объясним
филлом; выше заявки — глюк (52.2→522.0 при заявке 52.2 по-прежнему ловится).

🔴 Второе последствие замёрзшего qty, кроме цифр: `sphere.close()` закрыл бы
**14.32 из 389.99** — недозакрытие живой позиции.
