**Дефект (`core/infra/ws_feed.py`, исправлен `736beb5`).** Егор: «живую цену в шину срочно,
это очень большое упущение».

```python
if _pcb is not None and self._ticker_updates % 10 == 0:   # БЫЛО
    # Throttle: публикуем каждый 10-й тик (не перегружать bus)
```

`_ticker_updates` — счётчик ОБЩИЙ по всем 567 парам. Задумано «не чаще N на пару»,
получилось «одно событие из десяти по всему потоку»: ликвид проскакивал часто, неликвид
почти никогда. В памяти бота тик был мгновенный (`_ws_prices[symbol]` на каждый тик —
это читает трекер сделок), а шина, хаб, терминал и дашборд видели цену минутной давности.

**Лечение:** порог ПО СИМВОЛУ И ВРЕМЕНИ, два режима в конфиге —
`performance.ws_bus_publish_sec: 15.0` и `ws_bus_publish_priority_sec: 1.0`.
🔑 Приоритет берётся ИЗ ШИНЫ (`open_trade_id` / `watchlist`, кеш 10 с), а НЕ из `_active_ohlcv`:
`update_priority_pairs` после отката к Phase A/B — заглушка (`return`), подписок OHLCV нет
(селфтест `ohlcv=0`), опора на них дала бы приоритет НИКОМУ.

**Замер в бою (возраст цены в хабе, 573 пары):**

| | было | стало |
|---|---|---|
| p50 / p75 / p90 | 81 / 123 / 218 с | **8 / 15 / 17 с** |
| пары с открытой сделкой | 221 с | **3–4 с (все 8)** |

Нагрузка не изменилась: lag event loop 0.016 с, slow callbacks 0.

**Путь задержки до потребителя (для скальпинг-терминала — три troттлинга, все в конфиге):**
тик в памяти → `ws_bus_publish_priority_sec` (1 с) → шина → `cube_hub.flush_sec` (1 с) → хаб →
опрос читателя. Отсюда наблюдаемые 3–4 с; каждый шаг уменьшается параметром.

**How to apply:** любой троттлинг по счётчику событий РАЗНЫХ сущностей — ошибка; порог берётся
по ключу (символ/пара) и по времени. Искать такие места: `% N == 0` рядом с общим счётчиком.
