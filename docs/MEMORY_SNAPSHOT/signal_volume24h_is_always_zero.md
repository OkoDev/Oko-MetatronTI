# 🔴 Оборот в сигнале — признак-ПУСТЫШКА (найдено 29.09.2026)

`features_json.volume_24h` и `price_change_24h` равны **0.0 у всех проверенных 922 сделок**
четырёх механик: `rangefade4h` (95), `choch_wavec` (41), `radar_pump` (386), `impulse_fib_15m` (400).
Ключ есть, значение всегда нуль — поэтому «заполненность 74/74» ничего не значит, проверять надо
РАСПРЕДЕЛЕНИЕ, а не наличие ключа (я на этом споткнулся дважды за один разбор).

**Причина не архитектурная, а недоделка лупов**: они конструируют контекст с захардкоженным нулём —
`bot/loops/rangefade_loop.py:386`, `radar_armed_loop.py:1086`, `impulse_fib_runner.py:544`,
`ds_advisor_loop.py:67`, `scan_loop.py:1149`, `waves_long_loop.py:176`
(`MarketContext(..., volume_24h=0.0, price_change_24h=0.0)`).
А `method_egor_loop.py:245`, `method_v2_loop.py:201`, `oko_ote_observer_loop.py:339`,
`ote_observer_loop.py:365` передают реальный `vol24` — значит данные доступны, просто не переданы.

## 🔴 КОРЕНЬ (29.09): у оборота НЕТ единого источника, хотя сфера для этого есть

1. `MarketContext` (`core/signals/signal_models.py:187`) объявляет `volume_24h` **обязательным**
   полем без дефолта — каждый луп ВЫНУЖДЕН что-то передать, и передаёт `0.0`.
2. В шине оборота **нет места**: `PairState` (`core/context/pair_context.py:96-108`) хранит
   `tick_price`, но поля оборота у него нет вообще. При этом каталог шины обещает
   `TICK_PRICE: {price, volume_24h}` (`bus_catalog.py:140`, `pair_context.py:41`), а обработчик
   на `pair_context.py:700` берёт из события ТОЛЬКО `price` — оборот выбрасывается.
3. Поэтому четыре лупа, которым оборот нужен, идут в обход шины: `method_egor_loop.py:224`
   дергает `data_collector.get_ticker()` ПО СЕТИ на каждый сигнал — ровно та дублирующая
   качка, что описана в [[market_data_duplicated_fetches]].

## ✅ ПОЧИНЕНО 29.09 (коммит `2704bb5`) — одной правкой в сфере, а не шестью в лупах

`PairState` хранит `volume_24h` / `volume_24h_time` / `price_change_24h`, обработчик `TICK_PRICE`
их наполняет, `get_full_state` экспортирует. `MarketContext` получил дефолты `0.0`.
Единственная точка сборки — `core/context/context_factory.build_market_context(bot, symbol, ...)`:
шина → кэш тикера (**сеть не дёргается**) → честный ноль; прочитанное из кэша оседает в шине.
Шесть лупов переведены на фабрику. Тесты `tests/unit/test_market_context_factory.py` 15/15.

🔴 **Первая версия правки НЕ дала бы эффекта — проверка после рестарта это вскрыла** (коммит
`a3c5797`): оборот попадал в шину только из `TICK_PRICE`, а **WsFeed отключён**
(`performance.ws_enabled=false`, DEV-230) — событие не приходит вовсе. Вторая ветка фабрики
опиралась на `data_collector.get_cached_ticker`, **которого в проекте нет** (его зовут через
`hasattr` и получают None). Оба источника мёртвые.
**Рабочий источник — свечи, которые scan_loop уже держит:** оборот = сумма `volume × close`
за последние 24 ч бара входного ТФ → в `OHLCV_UPDATED` → `PairState`. Сеть не трогается.
Сверено на реальных свечах: BTC 1h ≈ 18.2 млрд USDT/сут, VET 1h ≈ 10.8 млн, TRX 15m ≈ 47.5 млн.
Урок: **проверять не «код положил значение», а «событие вообще приходит»** — источник может быть
выключен конфигом.
🔴 Старые 922 сделки НЕ восстановятся — оборот появится только в новых; для разбора прошлого
брать оборот извне (`universe_daily`, свечи Сферы 1).

**Правка должна быть ОДНА, а не в шести лупах:** поле оборота в `PairState` (наполнять из
`TICK_PRICE` и из свечей Сферы 1 — сумма quote-объёма за 24 ч) + дефолты `0.0` у `MarketContext`
и одна фабрика контекста, которую зовут лупы. Это усиление центральной сферы Куба, а не новый слой.

**Why:** ликвидность — одна из обязательных осей протокола вердикта. Пока поле нулевое,
**любой срез по ликвидности на боевых сделках этих механик невозможен**, и его нельзя записывать
в «проверено». Хуже: `trading_intelligence.py:2293` сравнивает `volume_24h < volume_threshold` —
гейт минимального оборота на таком контексте либо не работает, либо режет всё подряд, смотря по знаку.

## 🔴 ВТОРОЕ ПОЛЕ-ПУСТЫШКА: `live_orders.slip_pct` = 0 у ВСЕХ 20 436 ордеров (30.09)

Проскальзывание пишется нулём за весь период 04.04 → 30.09. Следствие прямое: **фактический
кост мы не знаем**. Записанные «косты 0.35%» ([[live_root_cause_costs_eat_tight_stops]]) —
оценка августа, а не измерение; из конфига проверяется только комиссия
(`simulation.taker_fee_pct: 0.045` × 2 стороны = 0.09%), остальные 0.26% ничем не подтверждены.
Любой вывод вида «косты съели эдж» опирается на неизмеренную величину.

**How to apply:** прежде чем предлагать фильтр по ликвидности или объясняять результат «мусорными
монетами» — проверить, есть ли оборот В ДАННЫХ. Для среза по ликвидности сейчас годится только
внешний источник (`universe_daily`, ticker на момент сделки), а не `features_json`.
