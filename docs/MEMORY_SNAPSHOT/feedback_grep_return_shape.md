# grep-before-claim распространяется на форму данных, не только на имена

При ревью/утверждении **порядка элементов tuple, имён полей, сигнатуры return** — グrep'ать сам `return`, а не вспоминать по памяти. Даже (особенно) если это МОЯ собственная функция.

**Why:** 02.06.2026, ревью ARCH-126 (swarm_orchestrator). Я насчитал «tuple-order баг R1» правильно по сути, но прежде сам же написал `team_ask.get_answer` → `(provider, model, text)` и в той же сессии при первом ответе пользователю описал её сигнатуру по памяти, не сверившись. Иронично — при действующем правиле [[feedback-no-fabricated-apis]] / grep-before-claim. Реальный функциональный баг (дирижёр синтезировал по именам моделей вместо ответов) поймал второй агент-ревьюер, не я.

**Расширение (02.06, 3-й catch за день):** ошибка бывает не в синтаксисе, а в **ПОСЫЛКЕ** о поведении — «дирижёр шлёт collect_context() каждый брифинг» (на деле для market_brief шлёт req.snapshot; я это читал в `consult()` в той же сессии и всё равно заявил неверно). Перед утверждением «модуль X делает Y» — перечитать ветку прямо сейчас, не по «помню, что читал».

**How to apply:**
- Перед утверждением «функция возвращает (a, b, c)» / «поле называется X» — `Grep "return \(" path` или прочитать определение. Не по памяти.
- В контрактах между агентами (один пишет producer, другой consumer) форма данных = поверхность бага. Сверять обе стороны grep'ом: и `return`, и распаковку.
- Урок процесса: **второй независимый агент-ревьюер ловит то, что автор не видит** (slepое пятно). Не пропускать ревью на «очевидном» коде — там и прячется R1/R2.
- Связано: [[feedback-no-fabricated-apis]] (существование метода), [[arch125-metatron-kernel]] (рой = гипотезы, не истина — то же про tuple-форму).
