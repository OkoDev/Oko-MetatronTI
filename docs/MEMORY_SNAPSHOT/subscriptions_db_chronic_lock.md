**29.09 шаг 2 (handle.exe, зонд v2 под pm2 `lock-probe`):** держатель — ВНУТРИ БОТА. Блокировка 02:45:30 → >11 мин
непрерывно; всё это время базу держат открытой только бот (10–32 соединения), dc_agent (8, запись 0) и терминал (1,
чтение); посторонних процессов нет; WAL не растёт → открытая НЕзафиксированная транзакция. Полосы совпадают с ДОЛГИМИ
проходами S20 (wave_loop 208–1045 с против обычных 36–60 с) — S20 в базу не пишет, он жертва той же перегрузки цикла.
Механизм-кандидат (самоподдержка): корутина держит транзакцию через await, а жертвы в цикле событий синхронно ждут
блокировку (`SubscriptionManager.record_signal_sent`: busy_timeout 10 с × 4 попытки) → цикл стоит → держатель не может
дойти до commit. Статический разбор (DML→await, DML в цикле, f-строки) бот не нашёл. Готов `core/infra/sqlite_txn_watch.py`
(включается OKO_SQLITE_TXN_WATCH=1, подключён в oko_mtf.py, инертен без переменной): лог «транзакция открыта >5 с» +
место создания соединения. Нужен рестарт бота с переменной — решение Егора.
**29.09 03:11 бот перезапущен С ТРАССИРОВКОЙ** (Егор: «С трассировкой»; `$env:OKO_SQLITE_TXN_WATCH='1'; pm2 restart
oko-bot --update-env`). Переменная теперь сохранена в pm2 и переживёт обычный `pm2 restart`; выключить —
`$env:OKO_SQLITE_TXN_WATCH='0'; pm2 restart oko-bot --update-env`. Полоса 02:45:30 держалась ~20 мин и отпустила САМА
в 03:05:39 (до рестарта) — запись в WAL стояла 02:45:23→03:05. Ждать строку `[TXN-WATCH] транзакция записи открыта`
в oko-bot-out.log → там место создания соединения-держателя. Гипотеза: исключение после DML, сохранённое где-то →
трассировка держит соединение до сборки цикла ссылок (длительность полос случайна: минуты…2 ч).
