Проверка панели «22 DRIFT» 30.08.2026: дрейф РЕАЛЕН. REST по обоим аккаунтам (acc1: 11, acc2: 12 = 23 позиции)
против БД (46 OPEN VST) → 23 записи-зомби, обратных орфанов 0. Возраст 6-42 ч, нотионал ~$3595.

**Три звена одной дыры (все три подтверждены логом):**
1. `sphere_cutover: true` + `sphere_shadow: true` → close-by-price в `position_sync` ВЫКЛЮЧЕН
   (`for trade in (() if _cutover else open_sim)`), а симулятор при exchange-managed сделке
   печатает `[LIVE-GUARD] ... ждём sync/биржу, разбор в position_sync` и НЕ закрывает.
   Разбора, на который он ссылается, при cutover не существует. Кольцо разомкнуто.
2. Бот перезапускается ~каждые 35 мин (pm2 `oko-bot` restarts=256). Закрытия в окне даунтайма
   не приходят как `pa=0`; `Sphere.init_account` (cold_start) наполняет store ТОЛЬКО живыми
   позициями ⇒ `reconcile_watchdog` (идёт по store, не по БД) их не видит: `reconcile_ws_drop` = 0 за весь лог.
3. Когда событие ВСЁ ЖЕ пришло — `close_trade` может упасть на `database is locked`
   (`[db_writer] #58702 ACU → SL ok=False`), ретрая нет, а store уже сделал `drop` ⇒ второго шанса нет.
   За 7.5 ч: 400 `database is locked` в логе, 2 из них — прямо в `close_trade`.

Единственная страховка — VST-time-exit по TTL 3-4.5 дня, т.е. зомби живёт до трёх суток.

**Цена (не в деньгах, а в потоке и в приборах):**
- `dedup_open`: 70 из 238 дропов за 2 дня — отказ входа из-за НЕСУЩЕСТВУЮЩИХ позиций (+83 `dedup`).
- Панель: Open P&L −14R это зомби (−16.61R), живые 23 позиции дают +0.96R / +$2.92 — отсюда
  противоречие «−14R при +$3». R считается по строкам БД, доллары по позициям биржи.
- `live_orders` у всех 23 уже `CLOSED` (мост знает о закрытии) — расхождение живёт только в `simulated_trades`.

Класс: [[bug_gate_lives_in_two_places]] + [[zombie_open_without_pid_lifecycle_hole]] — каждый механизм
отдаёт ответственность следующему, и при cutover цепочка обрывается. См. также [[orphan_root_dbexch_desync]],
[[bug_watchdog_restarts_healthy_bot]].

## ✅ ЛЕЧЕНИЕ (30.08, по слову Егора «устраняем первопричину и корень»)
1. `core/execution/db_writer.py::apply_exit_to_trade` — общая точка закрытия для WS-пути и
   реконсилиатора. Адресует строку **по id** (`find_open_exchange_trade` берёт последнюю по
   symbol+direction: при двух OPEN одной стороны — MYX SHORT #58595/#58605 — закрыл бы не ту)
   и **ретраит на `database is locked`** (4 попытки, 0.5/1.0/1.5с; между ними проверяет, не
   закрыл ли строку другой путь).
2. `core/exchange/position_sync.py::_db_reconcile` — сверка **от БД**, а не от store Сферы:
   OPEN-строка с биржевым order_id, которой нет среди позиций ≥2 циклов подряд (grace 300с) →
   exit тем же каскадом (REST filled по positionId → income) → закрытие. Не резолвится → не гадаем.
3. `scripts/heartbeat_watchdog.py`: `LIMITS` scan 1200→2700, tracker 480→1200. Замер по 6 файлам
   лога (2422/2474 замера): scan p99 1109с при пороге 1200, tracker p99 441с при пороге 480 —
   **порог снова стоял на краю нормы**, третий раз подряд (11.08 · 18.08 · 30.08).
4. `scripts/close_db_zombies.py` — разовая уборка накопленного, dry-run по умолчанию.
   Резолв дотянул реальные exit'ы для 20 из 24 (4 без `position_id` — их добивает time_exit).

**Подтверждено в бою (30.08 11:39):** `_db_reconcile` закрыл #58720 JASMY SL @ 0.004602 с первой
попытки — ту самую запись, по которой симулятор 15 ч писал «SL detected… ждём position_sync».
Три оставшихся (HMM · BCH · CHZ) он проверил и отказался закрывать: без `position_id` закрывающий
ордер не отличить от чужого. Итог: OPEN VST 46 → 25 при 22 позициях на бирже.

🔴 СЛЕДУЮЩИЙ КОРЕНЬ (не тронут): `database is locked` — не гонка, а СОСТОЯНИЕ. Уборка при живом
боте не прошла ни разу за 4 попытки; после `pm2 stop` write-lock освободился за 0.0с. При WAL и
`busy_timeout=10с` это значит: писатель держит лок дольше 10 секунд. Главные потребители —
`arch104_observer_loop` (185 локов за 7.5ч) и `decision_trace` (109). БД 1.34 ГБ.

🔑 Урок к [[bug_watchdog_restarts_healthy_bot]]: **порог, поставленный по сегодняшнему p99,
устаревает вместе с системой**. Скан деградировал (rate-limit баны, OHLCV 44с на пару), 20 мин
стали нормой — и порог 20 мин снова начал резать норму. Порог обязан стоять между хвостом
нормы и НАСТОЯЩЕЙ смертью (разрыв в два порядка), а не рядом с p99.
