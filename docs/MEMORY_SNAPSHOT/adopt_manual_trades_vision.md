# 🎯 ADOPT: ручная сделка → бот ведёт (важный момент, 12.06.2026)

Юзер: «а я могу открыть сделку которую будет бот вести?! я открываю — бот ведёт?». Помечено как **важный момент** (backlog, не делать наспех). Прямо в вектор **«почти торговый терминал»** (не просто дашборд).

**Сейчас:** бот ведёт ТОЛЬКО свои сделки — записанные им в `simulated_trades` (entry_price, original_sl, tp, regime, exchange_order_id). Вся логика ведения (TSL после +1R, SL/TP-мониторинг, exit) читает из БД. Ручная позиция → нет записи в БД → `sync_positions` метит её `exch-only` (те самые «22 exch-only» на дашборде) и НЕ трогает.

**Идея (adopt/усыновление):** EXEC-WS ловит `ORDER_TRADE_UPDATE FILLED` (ручное открытие) в реальном времени → создаёт tracked-запись в БД → бот начинает вести как свою. Тот же канал, что строится в EXEC-WS [[exec_ws_vst_userdata_proven]].

**Открытые вопросы дизайна (что решить ПЕРЕД реализацией):**
- **SL/TP — корень:** бот ведёт по 1R (TSL активируется после +1R), у ручной сделки 1R неизвестен. Варианты: (а) юзер ставит SL руками → бот берёт его как `original_sl`; (б) бот сам назначает SL при adopt (ATR/за свечу реакции). Юзер пока не выбрал.
- entry_price — из WS-события (`ap` avg price), есть.
- regime/signal_type — бот считает из текущего контекста пары при adopt.
- Как отличить РУЧНОЕ открытие от ботовского в WS-потоке (иначе бот усыновит свою же сделку дважды). Маркер: orderId которого нет в БД + не из ботовского place.

**Статус:** backlog. Сначала доделать базовый EXEC-WS (чтение exch_id/sync_close), adopt — следующим этапом. Связь: [[hedge_close_multiacct_root]] (тот же multiacct-routing нужен при ведении adopted на суб-акк), vision «Куб→Тессеракт→Сингулярность».
