# 🔴🔴🔴 ЖИВОЙ ВХОД ≠ ПРОВЕРЕННЫЙ ВХОД: бой не требует разворота WT (12.08.2026)

## Расхождение (обе строки проверены grep'ом)
```
БОЙ      bot/loops/rangefade_loop.py:187
         if not (at > 0 and w1 < thr):                      # ← и всё
БЭКТЕСТ  scripts/test_bos_gate_bigflush.py:121  и  test_bigflush_stacked_gates.py:122
         if not (tr_[i] > 0 and w[i] < -60 and w[i] > w[i-1]):   # ← ПЛЮС разворот WT
```
Живой вход срабатывает **всё время, пока WT под порогом** — то есть ловит падающий нож.
Бэктест входит **только в момент разворота** (WT начал расти). Это разные стратегии.
Условие общее для всех VARIANTS → касается `rangefade`, `rangefade4h`, `bigflush15`.

## Как нашёл
Сверил 63 живых сигнала `bigflush15` из логов (окно 08–31.07, где есть и логи, и кэш)
с бэктестовым условием на тех же барах:
| исход сверки | доля |
|---|---|
| **ни на формирующемся, ни на закрытом — условия НЕТ** | **44.4%** |
| условие держится на обоих | 28.6% |
| нет данных в кэше | 17.5% |
| только на формирующемся (бэктест не увидит) | 7.9% |
| только на закрытом | 1.6% |

Примеры «сигнала нет»: VANA 31.07 в 03:38 / 03:40 / 03:42 / 03:44 / 03:46 — один и тот же
сетап повторяется каждые 2 минуты (`POLL_SEC=120`), WT на формирующемся −80.4 при −76.4
на закрытом, то есть **WT ПАДАЕТ**. Бэктест такой вход не берёт.

## Что это объясняет
1. **Почему живьё убыточно, а бэктест прибылен.** VST: WR 26.5%, медиана −0.47%,
   сумма −9277% ([[drops_counterfactual_gates_clean]]); бэктест боевой стопки: WR 62%,
   медиана +1.13%, PF 2.55 ([[stacked_gates_joint_robustness_p7]]).
2. **Почему не собираются кластеры** ([[bigflush_frequency_collapse_stacked_gates]]):
   живые сигналы размазаны по времени (пока WT под порогом), бэктестовые точечные
   (момент разворота) → 4127 живых срабатываний РАВНОМЕРНО по минутам часа.
3. Почему живые сигналы повторяются каждые 2 минуты по одной монете.

## Сделано
Добавлен **SHADOW-замер** (`_wt_rising_closed` + лог `🔬 SHADOW-WT ... разворот_на_закрытом=`)
— считает, прошёл бы сигнал условие бэктеста. **Поведение НЕ меняет**, копит статистику.
Бот перезапущен 12.08 ~01:1x UTC.

## ✅ SHADOW НАБРАЛ ВЫБОРКУ: доля подтверждена, вывод не изменился
Через несколько часов работы: **True 309 / False 207 (n=516)** → **40% живых сигналов
действительно приходят БЕЗ разворота WT на закрытом баре**. Ранняя сверка с кэшем
(«44% не проходят») оказалась ВЕРНОЙ по доле; ошибочной была только первая партия
(24 True / 0 False), по которой я поспешил усомниться.

**Но вывод от этого не меняется:** прогон «с условием / без условия» на одном окне
даёт 60% против 59% WR. То есть 40% сигналов ДРУГИЕ, а результат ТОТ ЖЕ.
Это усиливает закон: **доля затронутых сигналов ≠ влияние на результат.**

## 🔴🔴 ЗАКРЫТО 12.08: РАСХОЖДЕНИЕ РЕАЛЬНО, НО ВЛИЯНИЕ ≈ НОЛЬ
Прогнал бэктест в ДВУХ вариантах на одном окне (42.9 мес, 30 ликвидных монет,
`scripts/fade_matrix_tf_side_phase.py … norev`):

| 4h LONG | n | WR | МЕД | PF | безтоп10% |
|---|---|---|---|---|---|
| с разворотом (как БЭКТЕСТ) | 518 | 60% | +3.74% | 1.69 | +264 |
| **без разворота (как БОЙ)** | 530 | **59%** | **+3.66%** | 1.65 | +232 |

На 1h так же: +1.13% против +0.99%. **Условие `w[i] > w[i-1]` отсеивает всего
12 сделок из 530** — на 4h почти все сигналы `WT<−60` и так приходят на развороте.

**Моя центральная гипотеза сессии ОПРОВЕРГНУТА собственным замером.**
Правку входа делать НЕ нужно — она ничего не изменит.
Shadow-замер (24 True / 0 False) говорил это сразу, а я счёл его недостаточной выборкой;
на деле он был прав, а моя сверка «44% не проходят» оказалась артефактом
(мерил ФОРМИРУЮЩИЙСЯ бар и на 15m, где условие ведёт себя иначе).

**Урок: расхождение КОДА ≠ расхождение РЕЗУЛЬТАТА.** Прежде чем звать дефект
причиной убытков — измерить его цену прогоном «с ним / без него» на одном окне.
Это дешевле и честнее любых рассуждений о механизме.

**Разрыв бой/бэктест остаётся НЕОБЪЯСНЁННЫМ** (живой rangefade4h WR 42.4% против 60%,
p=0.0029 — значимо). Исключены: исполнение (проскальзывание 0.000%, 0% входов хуже
сигнала), порог стопа (включение вредит по живым данным), разворот WT (влияние ≈0),
статистика (значимо). Остаются: **вселенная/survivorship** (бэктест на 30 монетах
с полной историей 3.5 года = выжившие; бой торгует 550 пар с новыми листингами)
и **фаза живого окна** (10 дней).

## ⚠️ Старая оговорка (сохранена для истории)
Первые 18 shadow-замеров: **10 True, 0 False**, 8 None (у rangefade4h API отдаёт <35 баров).
Ноль False ставит под вопрос МАСШТАБ находки. Возможная причина расхождения:
- сверка с кэшем считала разворот на **формирующемся** баре (`w[idx] > w[idx-1]`),
- shadow считает на **последнем ЗАКРЫТОМ** (`w[-2] > w[-3]`).
Это разные величины: на закрытом баре разворот может быть чаще.
**Факт расхождения кода остаётся железным** (строки 187 против 121/122 — grep),
но доля сигналов, которые реально отсеялись бы, пока НЕ установлена.
Решать только после накопления shadow (нужно ≥100 записей с не-None).
Если доля False окажется мала — правка входа не даст эффекта, и корень
убыточности надо искать в другом месте.

## 🔴 НЕ СДЕЛАНО (решение Егора)
Привести живой вход к бэктестовому (`w[-2] < thr AND w[-2] > w[-3]` по закрытым барам).
Это меняет входы ТРЁХ боевых источников сразу: частота упадёт, качество должно вырасти.
Делать только после разбора shadow-статистики.

## ЗАКОН
**Условие входа в бою обязано быть тем же выражением, что прошло прокурора.**
Один пропущенный конъюнкт (`w[i] > w[i-1]`) превращает «вход на развороте» во «вход
в падение» — и все бэктест-метрики становятся неприменимы к живому боту.
Родственно [[verdict_gate_dead_enum_str]] и [[sed_incident_5_flags_off]]:
третий за сессию случай «конфиг/код говорит одно, бой делает другое».
