# 🔴🔴🔴 RR-гейт убивал валидированный эдж молча (30.07.2026)

## Что было
`rangefade`/`rangefade4h` (ядро 4h ATRTrend↑+WT<−60 → LONG **TP1R**) за сутки живого VST дали
**0 сделок**. Я сначала подумал на конфиг (enabled), потом на мусорные монеты (WT −300 у неликвида) —
оба не были главной причиной.

## Настоящая причина
Роутерный гейт `rr_filter` (`core/trading/gates/rr_filter.py`) требует `trading.min_rr_ratio` = **2.0**.
Стратегия TP1R даёт RR ровно **1.00** → гейт режет КАЖДЫЙ сигнал:
```
⛔ 2Z/USDT:USDT [rangefade4h] WT=-62 отклонён: rr_filter:RR=1.00 < min_rr=2.0
```
Гейт `HARD` → регистрация не происходит вовсе. **Ирония: правило «RR≥3» мы сами опровергли**
(см. [[encyclopedia_rules_tested]]: RR<1 → +1.6%), но живой гейт продолжал его навязывать.

## Почему не нашли раньше
Луп логировал ТОЛЬКО успех (`res.trade_id`), а отказ уходил в тишину — `SubmitResult.hard_drops`
никто не читал. Добавил лог отказов в `bot/loops/rangefade_loop.py` → причина всплыла за одну минуту.
**Урок: любой луп обязан логировать ОТКАЗ с причиной, иначе гейт становится невидимой стеной.**

## Фикс
`config.yaml` → `trading.min_rr_per_strategy`: `rangefade: 0.95`, `rangefade4h: 0.95`
(0.95, не 1.0 — запас на float: `tp_dist/sl_dist` может дать 0.9999). Механизм пер-сорсовых порогов
уже существовал (`oko_ote: 0.1`, `radar: 0.5`) и уважается симметрично в `trade_simulator.py:453`.

## Класс проблемы (повторяется!)
Третий случай одной формы: **глобальный конфиг-гейт противоречит доказанному исследованию и молча
душит источник.** Родственники: [[bug_source_policies_deadpath_router_off]] (router off → гейт не
работает вообще). Правило: при заводе НОВОГО источника прогнать его сигнал через ВСЕ HARD-гейты
и проверить, что его конструктивные параметры (RR, SL-дистанция, объём) не конфликтуют с глобальными
порогами. Ставить пер-сорсовый порог СРАЗУ, не после суток тишины.
