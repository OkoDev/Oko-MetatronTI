Найдено 25.06 при разборе скрина Егора (TradingView, BTC, OTE-зона от октябрьского ATH 126208.5→спад, фибо 0.5=113983/0.62=116917/0.705=118995) — наш бэктест на confs=0 НЕ находил вообще НИЧЕГО рядом с этими уровнями для BTC за окт-ноя 2025.

**Корень (подтверждено прямым прогоном, не догадка):** `core/smc/oko_ote.py::detect_oko_ote` строка ~192: `h = select_significant_impulse(df_zone, _zz_zone)` — вызов БЕЗ аргумента `current_price`. `select_significant_impulse(df, zz, current_price=None)` (`smc_engine.py:781`) при `current_price=None` дефолтится на `df["close"].iloc[-1]` — **последний бар ПЕРЕДАННОГО df**. В бэктесте (`scripts/oko_ote_runner_test.py::test_pair`) `df_zone = _load(conn, sym, zone_tf)` грузит **ВСЮ историю** (для BTC 4h — 2022-01-01 → 2026-05-31), и `detect_oko_ote` зовётся **ОДИН РАЗ** на весь df с `only_latest=False`. Значит `current_price` = close на **2026-05-31** (73653.2) — конец ВСЕГО датасета, а не «сейчас» в момент каждой сделки.

**Прямое доказательство для BTC/USDT 4h:** `select_significant_impulse` с этим хиндсайт-current_price выбрал ногу **from 2025-10-06 (126208.5, тот самый ATH) → to 2026-02-06 (60000.0)**, direction=short, OTE-зона (93104.25, 112304.715). Нога ТЯНЕТСЯ до минимума, которого рынок достиг только в **феврале 2026** — будущее относительно ноябрьских/декабрьских сделок 2025, которые этой зоной оценивались. entry_fib=0.62 этой ноги ≈101049 — ТОЧНО совпадает с entry_px найденных сигналов (100246/100018/101160/...). Если усечь `df_zone` до `:2025-11-05` (как видел бы живой бот) — `select_significant_impulse` выбирает СОВСЕМ ДРУГУЮ ногу (апрель-май 2025, long, OTE 82332-93208) — то есть результат критически зависит от того, докуда обрезан df, что и есть определение lookahead.

**Почему это незаметно было раньше:** ВСЕ предыдущие $-тесты сессии (7 TF-комбо × 100 пар confs≥3, 3 sweep entry_fib, overlap-CSV-анализ) использовали ИМЕННО этот путь (`test_pair`→`detect_oko_ote(only_latest=False)`, полный df_zone без truncate) — то есть КАЖДЫЙ символ в КАЖДОМ из этих прогонов оценивался через ОДНУ статичную HTF-зону, выбранную с хиндсайтом по цене в конце ВСЕЙ истории (по большинству символов это ~май 2026). Сколько сделок реально искажено — неизвестно без point-in-time перепроверки per-символьно (зависит от того, насколько часто "значимый импульс" на конец датасета совпадает с тем, что видел бы бот в реальном времени — для некоторых символов может совпадать, для BTC — явно не совпало).

**Why:** живой код (`bot/loops/oko_ote_observer_loop.py`) НЕ страдает от этого — там `df_zone` естественно обрезан «сейчас» (свежие данные с биржи), `current_price=None` корректно дефолтится на актуальную цену. Баг СТРОГО бэктестовый — побочный эффект того, что `detect_oko_ote` не принимает per-bar `current_price` override для `only_latest=False`-ветки (она вызывает `select_significant_impulse` ОДИН раз снаружи цикла по сетапам, не пересчитывает зону на каждый бар входа).

🔴 **УТОЧНЕНИЕ (25.06, та же сессия, Егор показал слом на 4h/1h в момент пика) — ВТОРОЙ, отдельный механизм:** `find_setups_zz` (point-in-time, без хиндсайта) КОРРЕКТНО находит слом ровно у пика — 1h CHoCH bear 07.10.2025 (from=126208→to=120516), 4h CHoCH bear 10.10.2025 (from=126208→to=101516). НО `select_significant_impulse`, даже отсечённый СРАЗУ ПОСЛЕ слома (cutoff=11.10.2025, БЕЗ хиндсайта вообще), всё равно выбирает СТАРУЮ ногу апрель-май 2025 (+50% размах), А НЕ свежую октябрьскую (−20% размах) — потому что тай-брейк алгоритма (`smc_engine.py:790`, докстринг «цена в OTE → цена в ноге отката → **крупнейший span**») явно предпочитает БОЛЬШИЙ % размах среди ОДНОВРЕМЕННО «живых» (цена в диапазоне) кандидатов, не более свежий. Обе ноги были «живы» 11.10 (цена ещё в диапазоне обеих) — победил размер, не свежесть. **Значит проблема НЕ решается одним walk-forward пересчётом current_price** — даже идеально точный по времени пересчёт зоны унаследует этот же span-приоритет и может маскировать свежий, но МЕНЬШИЙ по размаху разворот в пользу старого крупного свинга. Нужно явно решать (с Егором): что важнее — самый крупный живой контекст (как сейчас) или самый свежий (recency-приоритет вместо/вместе с span)?

**How to apply:** НЕ чинить без решения Егора — масштаб правки серьёзный (нужен walk-forward пересчёт `select_significant_impulse` на срезе df_zone ДО каждого `ei`, а не один раз на полный df, это близко по духу к уже известному [[bug_fvg_overlap_held_lookahead]], но затрагивает САМ выбор HTF-зоны, не один из 6 confirmation-флагов — выше по значимости). **Результаты сессии 24-25.06 (memory/strategy_truth_state.md, раздел "OKO-OTE confs≥3 ВЫХОД-ТЕСТ") нужно читать с этой оговоркой — не объявлять edge подтверждённым до перевалидации с point-in-time-корректной зоной.** Кандидат-фикс (НЕ применён): в backtest-цикле пересчитывать `h = select_significant_impulse(df_zone.loc[:ei_ts], zz_zone_truncated)` лениво на каждый `ei`, либо хотя бы на каждый N-й бар — дороже по CPU, но честно.
