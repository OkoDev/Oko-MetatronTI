## 🔑 Дефект: ДВА РАЗНЫХ ЛИМИТА В ОДНОМ СЧЁТЧИКЕ

```sql
WHERE status IN ('OPEN','PENDING_ENTRY')   -- так считали ПЯТЬ лупов
```

Ожидающая лимитка **не в рынке**: не может ни выиграть, ни проиграть, рыночного
риска не несёт. Расходует она другое — **маржу под резерв**. Считая её слотом риска,
запрещали вход из-за расхода, которого нет.

Результат 22.08: **8 заявок держали кэп 8/8 при НОЛЕ позиций на бирже**, 1h-луп восемь
часов писал «скан 250 пар · новых 0». Позиций 0, риск 0, вход запрещён.

Починено: `core/trading/source_registry.slots()` — `max_open` (позиции = риск) и
`max_pending` (заявки = маржа) считаются раздельно. Применено в `impulse_fib_loop`
и `impulse_fib_15m_loop`; остальные пять — в [[backlog_strategy_registry]].
Потолок `max_pending` задаёт НЕ эдж, а маржа: 8 заявок ≈200 из 451 VST (~25/заявку).

## 🔑 ФИЛЛ-РЕЙТ ДЕГРАДИРУЕТ — «расхождение в 7 раз» ОТМЕНЕНО ПЕРЕМЕРОМ

Сначала намерил: замер **20.1%** против боя **2.9%** → «расхождение в 7 раз, p≈0.4%».
**Вывод был неверен: сравнивал бой (с гейтами) с замером БЕЗ гейтов.**

Перемер с гейтами (n=25361, 45 симв., вся история 1h):

    БЕЗ гейтов   n=20049   филл 22.4%   медиана импульса  8.11 ATR
    С гейтами    n=5312    филл 13.2%   медиана импульса 10.61 ATR

🔑 Механизм подтверждён контролем: с гейтами импульсы **сильнее** (10.61 против 8.11 ATR)
и наполняются **хуже**. Сильный импульс не даёт отката до 0.382 → **гейты и лимитный
вход конфликтуют ПО КОНСТРУКЦИИ**. Плата за качество — количество.

**Филл падает по годам** (с гейтами): 2023 **24.9%** → 2024 13.7% → 2025 **6.8%** →
2026 12.0%. При таких числах 1 успех из 35 — вероятность **~30%**, рядовой исход.
**Бой НЕ сломан.** Сторона: long 14.3% / short 10.3% (боевые 7 из 8 заявок — лонги).

⚠️ **Следствие важнее проверки:** заявленная в конфиге частота **~17 сделок/мес
ЗАВЫШЕНА** — она из эпохи с филлом 25%. При нынешних ~10% сделок вдвое-втрое меньше.
Это объясняет молчание лучше любого гейта.

**Вселенная проверена — разрыв НЕ объясняет** (2025+, гейты вкл.): top100 по обороту
**10.7%** (n=2928) против хвоста 9.1% (n=3064). Ликвидность влияет слабо.
Боевые 1/35 при филле 10.7% → p≈10%: необычно, но в пределах невезения на малой
выборке. **Расхождения бой↔замер НЕТ, механика работает как измерена.**

🔑 Настоящий потолок частоты — НАПОЛНЯЕМОСТЬ лимитного входа (~10%), а не кэп
позиций и не гейты. При 12 заявках за цикл заполняется ~одна.

НЕ проверено: режим года отдельно от календарного · кластер/одиночка ·
связь «филл ↔ PF по годам» (гипотеза: филл сам может быть индикатором режима).

## Диагностический маршрут «бот молчит» (проверять в этом порядке)

1. `pm2 jlist` + активность лупов в логе — жив ли процесс
2. кэп: `slots()` по источнику — позиций/заявок против лимитов
3. гейты: `loss_streak_halt` (3 убытка → пауза **72ч**), `min_sl_dist`, дрейф-гейт
4. биржа: openOrders/positions ТОЛЬКО через VST-домен, `load_dotenv(путь, override=True)`
5. `execution_mode`: SIM-записи (1688 за 14д) на биржу НЕ идут, VST — только 181

## ✅ DEV-239 ЗАКРЫТА 22.08: КЭПЫ РАЗВЕДЕНЫ ВО ВСЕХ ЖИВЫХ ЛУПАХ

Мина была не только у impulse_fib — **все живые источники имеют LIMIT-вход**
(проверено: ds_advisor, choch_wavec, rangefade, rangefade4h, bigflush15, atr_s2, radar).
Просто у остальных она ещё не выстрелила: PENDING у них не накапливался.

| луп | было | стало |
|---|---|---|
| `ds_advisor` | один счётчик, кэп 5 | 5 позиций / 5 заявок |
| `choch_wavec` | один счётчик, кэп 8 | 8 позиций / 8 заявок |
| `rangefade` (+4h, bigflush15) | один счётчик на СЕМЬЮ | позиции и заявки раздельно, семейная логика цела |
| `scan_loop` (atr_s2) | один счётчик, fail-closed | позиции/заявки раздельно |

🔑 **Кэп заявок по умолчанию РАВЕН кэпу позиций**, а не вдвое больше: рыночный риск
не растёт, поток восстанавливается, маржа раздувается умеренно. Урок из того же дня:
8 заявок при стопе 1.5% = 107% депо VST.

## 🔴 ЧТО НАМЕРЕННО НЕ ТРОНУТО
1. **Проверки «символ занят»** (`_symbol_busy`, dedup по паре) считают `OPEN+PENDING`
   ВМЕСТЕ — и это ПРАВИЛЬНО: заявка на символе означает, что второй вход не нужен.
   Развести их = получить две лимитки на одном символе при 100% корреляции.
2. **`method_egor` / `method_v2`** — выключены (`enabled: false`) и ключуются по
   `features_json LIKE`, а не по `signal_type`. Правка вслепую там бессмысленна;
   унификация ключа — DEV-238.
3. **`atr_s2`** оставлен на LIKE-ключе: записей в БД НЕТ ни одной, соответствие
   `signal_type` проверить нечем, а проверка fail-closed — промах ключа открыл бы кэп настежь.

**Проверка:** тест на синтетике 6/6 + сравнение со старой логикой показало ровно одну
целевую разницу (4 позиции + 4 заявки при кэпе 5: старая БЛОК → новая вход).
Рестарт → SelfTest 12/12, все три лупа подняты с новыми кэпами, ошибок нет.
