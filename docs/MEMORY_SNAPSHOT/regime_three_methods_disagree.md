## 2. Методы расходятся систематически

🔴 **ПОПРАВКА К СЕБЕ (важно для чтения таблицы ниже).** Сначала я записал «боевой —
`classify_from_ohlcv`, v2 в shadow». **ЭТО НАОБОРОТ.** `market_regime.use_v2: true` стоит
с **11.06.2026** (коммит `6a18516`), и строка `regime = _v2` затирала результат старого
метода. То есть **боевой классификатор — v2**, он и писал колонку `regime` во все
48 581 сделку, по которым сделан замер выше. Старый метод вызывался ВПУСТУЮ (04.09
холостой вызов убран). Подтверждение: распределение в БД (RANGE 37–71%) совпадает
с профилем v2, а не старого.
🔑 Класс ошибки тот же, что дважды за сессию: читать назначение по имени/комментарию
(«shadow logging») вместо проверки флага. `grep` конфига решал вопрос за минуту.

`classify_from_ohlcv` против `classify_v2` (боевой), 540 сравнений, все три ТФ переданы:

**СОГЛАСИЕ 41.9%** (случайное при 4 классах = 25%).

| | RANGE | TREND_DOWN | TREND_UP | HIGH_VOL |
|---|---|---|---|---|
| старый | 243 | 114 | 66 | **117** |
| v2 | 200 | **174** | **131** | 35 |

Расхождения не шумовые:
· `RANGE → TREND_DOWN` 12.2% и `RANGE → TREND_UP` 11.3% — v2 видит тренд там, где старый
  флэт. Совпадает с диагнозом в докстринге v2: «78% RANGE-сделок реально ТРЕНДИЛИ,
  15m-шум рассинхронизирует с 4h».
· `HIGH_VOL → TREND_*` 11.9% — старый втрое чаще объявляет высокую волатильность.
· 🔴 **`TREND_DOWN → TREND_UP` 3.9% — ПРОТИВОПОЛОЖНОЕ направление на тех же данных.**

## 3. Общий дефект всех трёх методов

`classify_from_ohlcv`, `classify_v2` и `classify_from_dataframes` меряют **ОДНУ МОНЕТУ**,
тогда как «режим рынка» — свойство РЫНКА. Проверенная альтернатива уже есть и работает
боевым гейтом: дрейф вселенной по 511 монетам ([[short_fades_bear_bounce_not_overheat]],
слепой тест PF 5.54 против базы 1.22).

обязательные срезы («сторона × год × режим»). Убрав её из записи, потеряем ось сравнения
прошлых замеров с будущими — а перемеры переворачивали выводы четырежды.

исторических сделках) · `classify_from_dataframes` (третий метод) в сравнение не входил ·
