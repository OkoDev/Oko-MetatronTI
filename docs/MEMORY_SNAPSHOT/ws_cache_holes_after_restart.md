Найдено 29.09 04:41, когда сборка текущего бара 1h/4h из 15m-кэша (Сфера 1 → бот, `core/infra/htf_from_store.py`)
в режиме shadow отказала 100% раз с причиной «short: есть 2 из 3 баров, всего 400». Снимок `cache/ohlcv_snapshot.pkl`:
дыры у 613/621 записей 15m, 387 5m, 426 3m — ровно на моментах рестартов бота (29.09 03:09, 03:30, 04:15, 04:24;
28.09 14:15–16:45; 15 записей — с дырой 261 бар от простоя 24–25.09). Механика: при рестарте кэш поднимается из снимка,
WS дописывает только НОВЫЕ бары (`merge_dict` append без проверки шага), пропущенные за простой никто не докачивает,
а TTL не истекает — WS каждую секунду «освежает» запись. Индикаторы ТФ входа (15m) считались на рядах с пропуском.

У BingX естественных пропусков нет (хранилище: 0 за 3 сут на 581 монете по 3m/5m/15m) → лечение безопасно:
`api_engine._drop_on_gap` (бар через пропуск → запись сбрасывается, следующий get → REST целиком) и `_has_gap` при
`load_from_disk`. Тесты `tests/unit/test_ohlcv_cache_gaps.py`. BACKLOG N18. Бот перезапущен с этим 29.09 04:44.

**29.09 вторая находка — НЕТОЧНЫЙ ФИНАЛ БАРА.** Прореживание в воркере MarketWS-v2 (3m 5 с · 5m 8 с · 15m 15 с) теряло
последние секунды бара: закрытые по потоку бары 15m (18 432) совпадали с биржей по close у 49.6%, по объёму у 18%.
И reader в главном процессе схлопывал пачку «последний выигрывает» — финал старого бара терялся под первым сообщением
нового. Лечение (`core/infra/market_ws_v2.py`): воркер досылает придержанное обновление перед сообщением следующего
бара; reader применяет финал старого бара до нового. После: 3m/5m 440 баров — 100% точно по всем полям.
🔴 **ПОПРАВКА 29.09 18:00 — «100%» была удачной выборкой без событий.** Полный замер 150 монет, 13:05–14:45 UTC:
в обычном режиме неточны 15m ~3% · 5m ~1.3% · 3m ~0.7% баров (в основном объём, изредка close); В СОБЫТИЯ — почти все:
15m-бар 14:15 и 5m 14:25 (закрытие 14:30 UTC) 143/148 и 137/148, 3m вокруг рестарта бота 14:33–14:36. Причина событий
не найдена (не опоздавшие финалы — stale ≈0; не супервайзор). После перезапуска потока ряды с разрывом сбрасываются, и до
REST-перекачки скана обновления WS по ним отбрасываются (5m skip_no_cache ~19 тыс. за 10 мин) — живых баров в очередь нет.
Вывод: бары из потока ≈ биржевые, но НЕ эталон; хранилищу нужна сверка задним числом по REST.
Сборка 1h/4h/1d из 15m у BingX точна (REST-15m → 514 тыс. баров, 100%), но из 15m очереди — наследует её ошибки.
На этом держится шаг 2 Сферы 1 (очередь `market_spool` → `market-store`, [[market_data_duplicated_fetches]]).

**Why:** дыра в ряду ломает любой индикатор с окном (WT, ATR, пивоты по барам) молча — ошибок нет, числа «правдоподобные».
**How to apply:** любой кэш рядов, который дописывается потоком, обязан проверять шаг при дописывании и при загрузке с
диска; «TTL свежий» ≠ «ряд цельный». Проверка непрерывности — первое, что делать при сверке двух источников баров.
