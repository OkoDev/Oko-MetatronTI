## Урок 1 — avg_R без распределения это ложь

### Что произошло

MultiSignalStrategy показывала avg_R = +3.486 на 511 сделках. Выглядело
как «редкие но крупные победители» — приемлемый профиль.

Реальность после SQL-среза:
- median_R = -1.000
- Sharpe = 0.261
- 20 сделок из 511 дали 65% всей прибыли
- Эти 20 сделок — один pump event 14.03 на трёх малоликвидных монетах
  (ARIA, RIVER, BANANAS31) с SL 0.1% (артефакт до DEV-157)
- Без этих 180 micro-SL сделок: avg_R = -0.348, Sharpe = -0.255

Стратегия не была «хвостовой» — она была убыточной, замаскированной
артефактом данных под прибыльную.

### Правило

Всегда смотреть четыре числа вместе, никогда одно:

```
n · WR · median_R · Sharpe
```

Если видишь только avg_R — это не метрика, это приглашение копать глубже.
Конкретные пороги для «стоит доверять»:

- **n < 100** — любые выводы шумовые, независимо от красоты цифр
- **Sharpe < 0.5** — стратегия живёт на удаче или хвосте
- **median_R сильно отличается от avg_R** — распределение с тяжёлым
  хвостом, среднее неинформативно
- **top-20 сделок дают >50% прибыли** — проверить, не одно ли это рыночное
  событие, посчитанное многократно

### Как не повторить

В `performance_engine.py`/`by_signal_type()` и везде, где выводятся метрики
стратегий (дашборд, TG-отчёты, docs/ROADMAP), добавить обязательный набор
колонок: `n · WR · median_R · Sharpe · p90_R · top20_share`.

Одной метрики avg_R в публичных документах быть не должно.

## Урок 2 — мёртвые стратегии молча искажают решения

### Что произошло

MultiSignalStrategy не имеет 0 сделок с 01.04.2026. Это 18 дней тишины.
Причина: детектор `confluence` отключён в DEV-171 (14.04) как убыточный.

Но:
- Метрики стратегии по-прежнему в БД и на дашборде
- Код стратегии жив в `strategies/built_in/confluence.py`
- State machine `confluence_state_machine` работает
- Флаг `enabled: false` в yaml легко обратим

Через 3-6 месяцев кто угодно — ты сам, новый DEV, Claude в новой
сессии — может посмотреть на avg_R = +3.486 в документации и сказать
«стратегия с таким avg_R, давайте вернём с более строгими фильтрами».
Это будет решение на основе мёртвого сигнала, принятое за живой.

### Правило

Стратегия или детектор имеет один из четырёх статусов. Промежуточные
не допускаются:

| Статус | Код | В арбитре | В метриках | Маркер |
|---|---|---|---|---|
| ACTIVE | жив | да | да | — |
| SHADOW | жив | нет, только лог | да, отдельно | `shadow: true` |
| DEPRECATED | жив | нет | **заархивированы** | `deprecated_at` |
| REMOVED | удалён | нет | заархивированы | git history |

Переход ACTIVE → DEPRECATED обязан:
1. Добавить `deprecated_at` в конфиг стратегии
2. Переместить исторические метрики в архивный раздел с пометкой
3. Убрать из активных дашбордов
4. Оставить запись в ROADMAP: почему отключили, какой edge исчез

Через N месяцев (6?) DEPRECATED → REMOVED. Код уходит в git history,
метрики остаются в архиве.

### Как не повторить

Ревизия раз в месяц: прогон по всем стратегиям и детекторам с SQL
«кол-во сделок за последние 30 дней». Ноль сделок — обязательный
статус DEPRECATED с датой.

Конкретно сейчас: `confluence`, `multi_signal`, любой детектор с 0
сделок post-01.04 нужно пометить `deprecated_at: 2026-04-14` и убрать
из активных метрик дашборда.

## Урок 3 — артефакты данных живут дольше, чем фиксы в коде

### Что произошло

DEV-157 (15.04) добавил guard `min_sl_dist_pct` — сделки с SL<0.1% больше
не регистрируются. Код исправлен.

Но в БД осталось:
- 180 из 511 сделок MultiSignal с SL<0.2%
- Неизвестное (не посчитано) число сделок других стратегий с той же
  проблемой
- Их R_multiple в десятки и сотни раз больше типичного
- Эти значения: влияют на avg_R всех агрегатов, попадают в обучающую
  выборку OutcomePredictor, искажают веса `update_signal_weights()`,
  создают иллюзию прибыльности pump-монет

DEV-174/175 (15.04) починили TSL-логику — ещё три бага. Всё, что
закрывалось по TSL до 15.04, закрывалось по неверным правилам.
Эти сделки тоже в БД.

Код чистый. Данные заражены.

### Правило

Любой фикс поведения, влияющий на регистрацию или закрытие сделок,
должен сопровождаться:

1. **Маркером эпохи в features_json.** Новое поле `data_era: "post-15apr"`
   для всех будущих сделок. Без эпохи — данные из разных режимов
   системы неразличимы и не должны смешиваться.

2. **Явной политикой использования.** Для каждого источника данных
   (OutcomePredictor.fit, update_signal_weights, performance_engine,
   дашборд) — решение, какие эпохи он читает:
   - ML train: только последняя стабильная эпоха
   - Анализ трендов: все эпохи, но разделённо
   - Метрики в дашборде: последние 30 дней (эпоха автоматически
     отсечётся временем, если фикс не слишком свежий)

3. **Скриптом split-анализа перед любым решением на исторических
   данных.** DEV-178 — это и есть такой скрипт, и он должен стать
   стандартной практикой, а не задачей одного аудита.

### Как не повторить

В `simulated_trades` ввести поле `data_era` (TEXT), заполняемое при
регистрации из константы в коде. При каждом значимом фиксе регистрации
или закрытия — инкрементировать константу (`v1`, `v2`, `v3`...).

В `OutcomePredictor.fit()` добавить параметр `min_era` — по умолчанию
текущая. Это делает невозможным случайное обучение на старых данных.

В ROADMAP фиксировать не только «что починили», но и «какие данные
это инвалидировало» — одна строка на фикс, но критически важная.

## Мета-урок — порядок имеет значение

Три урока выше не независимы. Они образуют цепочку ошибок:

```
артефакт в данных (урок 3)
    ↓
искажает метрику avg_R (урок 1)
    ↓
создаёт иллюзию рабочей стратегии
    ↓
стратегия уходит в DEPRECATED, но метрики остаются (урок 2)
    ↓
через месяцы кто-то решает "вернуть стратегию с avg_R = 3.48"
    ↓
повторение с новыми параметрами на тех же заражённых данных
```

Разорвать цепочку можно в любой точке — но надёжнее всего в начале.
Если `data_era` есть с самого старта, артефакт изолирован — урок 1 и
2 становятся менее критичными. Если data_era нет — любая стратегия
может тихо жить на призрачных метриках годами.
