# ARCH-153 — Актуальность рыночных данных: причины отставания, протухания и банов биржи

> Поставлено 27.10.2026 по требованию Егора: «так оставлять нельзя… сейчас 19:17, последняя свеча с задержкой —
> актуальность данных под вопросом». Статус: 🔴 срочно, блокер выхода на домен.
> Это не «аварийная починка», а **расследование причин**: до сих пор лечили симптомы (сирота на порту 27.10,
> рестарты, таймауты). Правило проекта: сначала измерить, потом чинить.

## Измеренные факты (пассивно, по логам — на биржу запросов не добавлялось)

1. **У бота есть собственный фон банов, не связанный с Монитором:** `100410` в `oko-bot-out.log` 27.10 по часам
   (локальное время): ночью 00–09 ч — **16–41 в час**; днём, при работе над фронтом, 11–15 ч — **105–196 в час**;
   16–19 ч — 58–83 в час. То есть ночью бот сам делает ~30 бан-событий/час при нулевой нагрузке от людей.
2. **Бан-события бота за 10–19 ч по таймфрейму запроса:** 3m — 313, 1h — 266, 5m — 235, 4h — 120, 15m — 97, 1d — 12.
   Основная масса — младшие ТФ.
3. **:8010 при открытии окна сам просит +400 баров на каждое окно** (измерено на 2×2: 8 запросов по 600 баров за 7 с,
   пользователь ничего не делал). Причина в коде: подписка `r.from<6` срабатывает от самой подгонки окна
   (`setVisibleLogicalRange({from:0,…})`). На 4×4 — порядка 32 запросов по 600 баров при каждом открытии,
   смене ТФ, листании страницы.
4. Терминал ходит на биржу **напрямую, мимо GlobalRateLimiter бота** (комментарий в коде от 16.08, structure_terminal.py:809):
   при бане продолжал «долбить» и держал бан. Стоп-кран `_ban` добавлен, но он только молчит 60 с, а не снижает поток.
5. Бот и терминал сидят на **одном IP**; у бота есть пул прокси («забанен ОДИН прокси»), у терминала — нет.
6. `/api/levels` терминала считает структуру по **1000 барам на монету** на каждый расчёт — это тяжёлые запросы к бирже;
   наш фронт при включённом слое «Куб» просит уровни по всем видимым монетам раз в 60 с.
7. Терминал при перезапуске 27.10 прогревается пачкой запросов (известно из памяти `pm2_windows_restart_orphans`);
   в тот день он стоял с сиротой на порту 132 часа — часть «протухания» была именно этим (устранено).

## Гипотезы (по убыванию правдоподобия; каждую надо подтвердить или закрыть измерением)

- **H1. Дубль нагрузки терминала на биржу:** автодогрузка :8010 + `/api/levels` по 1000 барам + прямые запросы мимо лимитера.
- **H2. Собственный фон бота** (~30 бан-событий в час ночью) — бот сам упирается в лимит на младших ТФ; терминал
  попадает в уже начатый бан, потому что IP общий.
- **H3. Общий IP + отсутствие приоритета:** боевой контур (бот) и аналитика (терминал, фронт) делят один лимит
  без разделения; любой «поглядеть график» отнимает у бота.
- **H4. Кэш терминала маскирует бан:** `_klines` при бане отдаёт старый кэш, а при пустом кэше — `[]`;
  ни то ни другое не помечено → протухание выглядит как «норма».
- **H5. Что-то периодическое** (скрипты pm2, сборщики: btc-flows, liq-ws, market-pulse, cache-freshness и др.)
  ходит на ту же биржу с того же IP — вклад не измерен.

## Критерии готовности

- возраст последней свечи у выбранных монет ≤ 2 интервалов ТФ **в 99% минут** за сутки (измеряется вахтой, п.4);
- бан-событий бота ночью ≤ целевого значения, которое утвердит Егор после п.1–3 (сейчас ~30/час);
- терминал и фронт **не отдают протухшие данные молча**: всегда явная пометка возраста (у фронта сделано 27.10);
- публичный контур (домен) не зависит от бана боевого терминала.
