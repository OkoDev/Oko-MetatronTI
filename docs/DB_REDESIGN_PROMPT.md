# Архитектурный вопрос: перепроектирование БД торгового бота в полноценный терминал

## КОНТЕКСТ
Торговый бот для крипты (BingX futures через ccxt). Python 3.12, solo dev, Windows.
БД: SQLite (WAL-режим), 24 846 сделок, 207 MB, есть система миграций (db_migrations).
Архитектура: 6 детекторов сигналов → симуляция сделок + реальное исполнение на бирже.
Режимы исполнения: SIM (чистая симуляция, ~60% сделок), VST (демо-биржа BingX) и LIVE.
Мультиаккаунт: бот торгует на 2+ суб-аккаунтах BingX (sticky-routing символов по аккаунтам).

## ТЕКУЩАЯ СХЕМА (факты)
Центральная таблица `simulated_trades` — ДЕНОРМАЛИЗОВАННАЯ, 50 колонок в одной таблице:
- сигнал: symbol, timeframe, signal_type, direction, strength, regime, source_router(=стратегия)
- цены: entry_price, stop_loss, take_profit, exit_price, tp1/tp2/tp3, original_sl, actual_entry_price
- результат: status, profit_pct, R_multiple, max_R_possible, captured_R_pct, first_profit_r, first_drawdown_r
- биржа: exchange_order_id, exchange_sl_order_id, exchange_tp_order_id, qty
- мета: features_json(TEXT), decision_trace_json(TEXT), strategy_name, sl_source, tp_source

Связанные таблицы:
- `live_orders` (10k): sim_trade_id ↔ exchange_order_id, sl/tp_order_id, status (связь сделка↔биржа)
- `account_routing` (459): symbol → account_id + mode (sticky какой символ на каком аккаунте)
- `trade_features` (9k): отдельная таблица признаков (FK на сделку)
- signal_drops (208k), signal_stats (139k), risk_decisions_log (27k) — аналитика/логи

ЧЕГО НЕТ (корень боли):
- НЕТ поля account в сделке → нельзя отличить сделку acc1 от acc2
- НЕТ поля execution_mode (SIM/VST/LIVE) → тип определяется КОСВЕННО (exchange_order_id IS NULL = SIM)
- НЕТ трекинга баланса по аккаунтам (текущий баланс агрегируется, история не хранится)
- НЕТ явного поля exchange (на будущее — Binance/Bybit)

## БОЛЬ (зачем переделываем)
1. SIM / VST / реальные сделки — всё в одной куче, реальный PnL не отследить
2. Нет разделения по аккаунтам — открытые позиции в одной куче, баланс каждого аккаунта отдельно не видно
3. Нужно ВИЗУАЛЬНОЕ подтверждение движения баланса по аккаунтам (не логи)
4. Фильтраций по сделкам будет ОЧЕНЬ много — разнотипных и перекрёстных
5. Возможно генерация отчётов
6. Цель — «почти торговый терминал», не просто дашборд

## ТРЕБОВАНИЯ НАПЕРЁД (проект в начале пути, закладываем развитие)
- Multi-exchange ready (Binance/Bybit/OKX когда выйдет в плюс)
- Multi-account scale (больше суб-аккаунтов)
- Баланс/equity по аккаунтам с ИСТОРИЕЙ (графики движения)
- Тяжёлая аналитика и отчёты
- Возможный переход SQLite → PostgreSQL при разнесении на процессы/машины

## ВОПРОСЫ (нужен ГЛУБОКИЙ разбор)
1. СХЕМА: оставить денормализованную (всё в simulated_trades 50 колонок) или нормализовать
   на сущности (accounts / trades / orders / fills / balances / signals)? Trade-offs для
   торгового терминала с тяжёлыми фильтрациями.
2. КАК СТРОЯТ РЕАЛЬНЫЕ ТЕРМИНАЛЫ: какие канонические сущности и связи у бирж/брокеров/
   trading-платформ? Order vs Position vs Fill vs Trade — как разделять? Ledger/event-sourcing
   подход для денег и балансов (immutable журнал транзакций)?
3. РАЗМЕТКА: execution_mode (SIM/VST/LIVE) + account_id + exchange — как лучше моделировать?
   Поля в сделке, или отдельные измерения/таблицы? Как чисто разделить симуляцию от реального
   исполнения (один поток с флагом vs раздельные сущности)?
4. БАЛАНСЫ: как трекать equity/баланс per-account с историей для графиков? Snapshot-таблица
   с периодичностью, или event-driven (каждое изменение)? Ledger подход?
5. ФИЛЬТРАЦИИ И ОТЧЁТЫ: много перекрёстных фильтров (по аккаунту×режиму×стратегии×режиму
   рынка×периоду). OLTP-схема достаточно с индексами, или нужен отдельный аналитический слой
   (витрины/materialized views/star schema)? Где граница?
6. МИГРАЦИЯ: 24 846 живых сделок, ломать нельзя. Как поэтапно мигрировать денормализованную
   таблицу в новую схему без даунтайма? Backfill: account ретроспективно неизвестен (не
   писался), execution_mode выводим из exchange_order_id. Стратегия?
7. SQLite → PostgreSQL: что заложить СЕЙЧАС в дизайн, чтобы будущая миграция была дешёвой?
   Какие SQLite-специфичные вещи избегать? Когда реально переходить?
8. ЧЕГО МЫ НЕ ПРЕДВИДИМ: проект в начале — какие сущности/поля/связи реальные торговые
   системы добавляют позже и жалеют что не заложили сразу? (fees, funding, partial fills,
   slippage, латентность исполнения, налоговая отчётность, аудит-трейл?)

Дай развёрнутый архитектурный разбор по каждому вопросу. Предложи конкретную целевую
схему (таблицы + ключевые поля + связи) и план поэтапной миграции. Приоритизируй: что
критично заложить сейчас, что можно отложить.
