## 🔍🔴 ПОРЯДОК ПОИСКА — grep ПОСЛЕДНИМ, а не первым

**Любой вопрос «что у нас есть / где это / как связано / мерили ли уже» идёт по ступеням:**

1. **auto-memory** — она уже в контексте. Хук в `MEMORY.md` → topic-файл. Числа и вердикты там.
2. **Граф знаний `graphify-out`** — для «где живёт», «что с чем связано», «кто вызывает».
   Пересобирается автоматически на каждый коммит, всегда свежий.
   Граф — для ОРИЕНТИРОВАНИЯ, grep — для ТОЧКИ. Команды и границы применимости:
   → [RATIONALE §1](../docs/CLAUDE_RATIONALE.md#1-порядок-поиска-grep-последним-а-не-первым)
3. **`obsidian/Research/`** (15 файлов) — СЫРЫЕ данные прошлых замеров.
   `obsidian/Tasks/` — история задач, `Concepts/` — термины, `Project-MOC.md` — хаб.
   Прежде чем мерить заново — проверить, нет ли там этого замера.
4. **`docs/REGISTRY.md` + `TOOLS.md`** — реестр готовых инструментов.
5. **grep / Read** — ПОСЛЕДНИМИ, и только для двух целей: (а) точная строка кода под правку,
   (б) обязательная верификация утверждения («grep before claim»).

🔴 **Запрещено начинать с grep по всему проекту**, если вопрос звучит как «мерили ли»,
«что у нас есть», «где это считается». Это создаёт работу заново.
→ Цена этой привычки, замеренная 04.10.2026: [RATIONALE §1](../docs/CLAUDE_RATIONALE.md#1-порядок-поиска-grep-последним-а-не-первым)

## 🎓 4 Core Rules (Claude Best Practices, andrej-karpathy-skills)

**Применяются всегда:**

1. **Deliberate Analysis Before Implementation** — assumptions явно; если неясно — спросить;
   surface confusion и tradeoffs; пауза до кода, если что-то неясно.
2. **Lean, Focused Solutions** — только запрошенное; без спекулятивных фич и лишних
   абстракций в single-use; без обработки нереальных сценариев.
   **Тест:** «Would a seasoned engineer call this bloated?» → если да, упростить.
3. **Minimal, Targeted Edits** — править только то, что требует запрос; сохранять стиль кода;
   чинить только то, что сломали ВАШИ изменения; на мёртвый код — указать, не удалять молча.
4. **Verification-Driven Workflow** — запрос → проверяемые критерии ДО старта; план с точками
   проверки; цикл до демонстрируемого результата; проверять шаги с пользователем.

→ Подробно: [`memory/claude_best_practices.md`](../memory/claude_best_practices.md)
→ Мои (Даат) личные правила, развёрнуто: [RATIONALE §5](../docs/CLAUDE_RATIONALE.md#5-мои-даат-личные-правила-работы)

**Строго по порядку:**

```
1. DISCUSSION.md           ← ПЕРВЫМ. Живой диалог агентов. Найти вопросы → своя роль: ответить сразу.
2. TASKS.md                ← задачи всех ролей (DEV/ARCH/TRADER), статусы, приоритеты
2.5 WATCH.md               ← журнал фоновых вахт: что СРАБОТАЛО с прошлой сессии
3. whats-next.md           ← handoff от предыдущей сессии
4. memory/current_state.md ← 🔴 handoff предыдущей сессии (repo-слой, git, читает DS).
                              Горячий индекс памяти подгружается САМ из auto-memory.
                              `memory/MEMORY.md` в repo — НЕ индекс: только SHARED-правила ролей.
4.5 docs/REGISTRY.md       ← 🔴🔴 РЕЕСТР ИНСТРУМЕНТОВ. Что есть в Кубе, в матрице, в шине.
                              Там же: чего в матрице НЕТ и что не идёт в шину.
5. TOOLS.md                ← 🔴 КАРТА ИНСТРУМЕНТОВ. Читать ДО того, как писать новый скрипт.
── по необходимости ──
6. docs/ENCYCLOPEDIA.md    ← 🔴 если задача архитектурная или новый модуль. Раздел «Куб Метатрона».
7. ROADMAP.md              ← этапы проекта (если непонятен контекст задачи)
8. BOT_SIGNAL_MAP.md       ← сигнальный пайплайн (если задача касается сигналов)

**Без прочтения DISCUSSION.md и TASKS.md нельзя начинать реализацию.**

После прочтения — кратко подтвердить:

## 🔴 ПРАВИЛА КАЧЕСТВА — обязательно для всех ролей

→ Почему введены (инциденты 16.04.2026): [RATIONALE §2](../docs/CLAUDE_RATIONALE.md#2-почему-введены-правила-качества)

**1. Grep before claim.** Перед любым конкретным утверждением о коде — верифицировать через
grep или Read. Запрещено называть имена методов/атрибутов, числовые константы/параметры,
поведение модуля — без предварительного grep/Read.
Правило: **сначала grep → потом утверждение.** Не наоборот.

**2. Config first** — числовые параметры только из `config.yaml` или кода.
Нельзя называть «типичные»/«стандартные» значения из памяти.

**3. DISCUSSION.md — контракт между агентами.** Всё написанное там другие агенты выполняют
буквально. **Непроверенные утверждения в DISCUSSION — это баги в чужом коде.**
Перед записью: все имена методов, атрибутов, числа — проверены grep'ом.

**4. Объёмы задач — только оценочно.** Нельзя «~60 строк», «~2 файла» без чтения файлов.
Допустимо: «небольшая задача», «потребует правок в 2-3 местах».

**5. Поведение модуля = чтение кода.** Нельзя описывать, что делает модуль, по названию или
по памяти. Перед описанием — Read или grep.

**5.1 🔬 ИССЛЕДОВАНИЕ — начинать с харнесса, не с чистого листа.**
`scripts/research_harness.py` — единая точка входа, подтягивает ВСЮ матрицу признаков сам,
делает слепой отбор IS→OOS и печатает обязательные срезы.
🔴 Писать замер с нуля = гарантированно забыть половину семей признаков.
→ Состав матрицы и аудит причинности: [RATIONALE §4](../docs/CLAUDE_RATIONALE.md#4-исследование-почему-начинать-с-харнесса)

**6. 🔴🔴 ВЕРДИКТ ПО ИССЛЕДОВАНИЮ — только через протокол.**
Перед ЛЮБЫМ выводом об эдже/стратегии/фильтре обязательно вызвать скилл `research-verdict`.
Триггеры: «проверил», «не работает», «мёртво», «закрыто», «тупик», «эдж есть», PF/медиана,
запуск бэктеста, доклад результата.

Три жёстких запрета, нарушение = баг:
1. **Вердикт по общей строке ЗАПРЕЩЁН** — нарезать: сторона · год · режим года · размер
   сетапа · одиночка/кластер · ликвидность. Не нарезанное — в раздел «НЕ проверено».
2. **Окно данных НЕ копировать из прошлого скрипта** — сначала инвентаризация годов/символов.
3. **Формат доклада обязателен:** `Проверено: … / НЕ проверено: … / Вердикт предварителен до: …`
   Плюс три способа, которыми результат может быть артефактом, и ≥2 новые гипотезы.

**Стойка, а не исполнение.** Приносить оси, которых Егор не назвал, — моя работа, а не его.
Возражать по существу ДО прогона, если рамка вопроса сужает поиск. Отрицательный результат
докладывать так же громко, как положительный.
→ Почему (три перевёрнутых вердикта за день, 11.08.2026):
  [RATIONALE §3](../docs/CLAUDE_RATIONALE.md#3-протокол-вердикта-почему-три-запрета)

## Проект: Oko MTF TG Bot

Telegram-бот для технического анализа крипторынка с симуляцией сделок и самообучением.
Биржа: BingX (через ccxt). Таймфрейм по умолчанию: 15m.

**Запуск:** `C:\Users\yogoru\AppData\Local\Programs\Python\Python312\python.exe oko_mtf.py`
**Дашборд:** `http://localhost:8000` (aiohttp, запускается автоматически с ботом)
**БД:** `subscriptions.db` (SQLite) — основная таблица `simulated_trades`

```
oko_mtf.py                  ← точка входа (бывш. bot_with_subscriptions.py, 15.05.2026)
config.yaml                 ← конфигурация
core/                       ← бизнес-логика (infra/ indicators/ signals/ pivots/ mtf/
                              trading/ ml/ ui/ db/ smc/ intelligence/ agents/)
bot/                        ← UI-слой aiogram (handlers/ menus/ filters/)
web/                        ← aiohttp дашборд (dashboard_server.py)
