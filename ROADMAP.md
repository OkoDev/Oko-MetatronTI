## 🎯 Этап 1 — Trade Simulator (фундамент интеллекта)

**Цель:** Каждая выданная рекомендация регистрируется как симулированная сделка; фоновый процесс отслеживает исход по SL/TP (по high/low свечей). Накапливаем данные для R-multiple и метрик.

### Шаги

1. [x] **БД:** Добавить таблицу `simulated_trades`
   - Поля: id, symbol, timeframe, signal_type, direction, entry_price, stop_loss, take_profit, strength, confidence, regime, created_at, status (OPEN/TP/SL/EXPIRED), exit_price, profit_pct, R_multiple, closed_at, duration_minutes, features_json (опционально)
2. [x] **Модуль:** Создать `core/trade_simulator.py`
   - `register_trade(recommendation)` — сохранение сделки при выдаче рекомендации
   - `get_open_trades()`, `close_trade()`, расчёт R и profit_pct
   - `check_open_trades(data_source)` — проверка OHLC, определение hit SL/TP/EXPIRED
3. [x] **Интеграция:** В точке выдачи рекомендации (после `analyze_symbol` в боте) вызывать `register_trade(recommendation)`
4. [x] **Фоновая задача:** Asyncio task / scheduler — раз в N минут вызывать `check_open_trades` (использовать существующий data_collector для OHLC)
5. [x] **Правила:** Чётко определить приоритет при одновременном hit SL и TP в одной свече; max_duration для EXPIRED (48 ч)

**Критерий успеха:** Рекомендации пишутся в БД, открытые сделки закрываются по SL/TP/времени, в таблице есть закрытые записи с заполненными R_multiple и profit_pct.

## 🎯 Этап 2 — Performance Engine (статистика)

**Цель:** Считать по закрытым сделкам winrate, avg R, expectancy, profit factor по типу сигнала (и при возможности по режиму/таймфрейму).

### Шаги

1. [ ] **Таблица/кэш:** `model_metrics` или расчёт на лету по `simulated_trades` (signal_type, regime, timeframe → winrate, avg_R, expectancy, total_trades, last_updated)
2. [ ] **API:** Функции вида `get_metrics_by_signal_type()`, `get_metrics_by_regime()` для использования в адаптации и в дашборде
3. [ ] **Дашборд/отчёт:** Простой отчёт в боте или лог: топ сигналов по expectancy, худшие по winrate

**Критерий успеха:** Есть воспроизводимая статистика по типам сигналов; можно принять решение, какие веса менять.

---

## 🎯 Этап 3 — Адаптивные веса от статистики

**Цель:** Веса в Trading Intelligence зависят от реальной эффективности (expectancy / winrate по типу сигнала), а не от фиксированных констант.

### Шаги

1. [ ] **Чтение метрик:** В месте расчёта весов (например в `_calculate_adaptive_weighted_strength` или аналоге) подставлять вес от Performance Engine (при отсутствии данных — дефолт)
2. [ ] **Порог минимальной выборки:** Не менять веса, пока по типу сигнала меньше N закрытых сделок (например 20–50)
3. [ ] **Режим «только наблюдение»:** Опционально не применять адаптивные веса до накопления 100–200 сделок

**Критерий успеха:** После накопления достаточной истории веса типов сигналов отражают их фактическую эффективность.

## 🎯 Этап 4 — Market Regime

**Цель:** Вводим режим рынка (trend / chop / high volatility и т.д.) и учитываем его при агрегации и в статистике.

### Шаги

1. [ ] **Метрики режима:** ATR percentile, slope тренда, сжатие волатильности (или простой классификатор: trend_up / trend_down / range)
2. [ ] **Сохранение в сделке:** При `register_trade` записывать текущий regime в поле `regime`
3. [ ] **Статистика по режиму:** В Performance Engine считать метрики по паре (signal_type, regime)
4. [ ] **Использование в решении:** При агрегации усиливать/ослаблять сигналы в зависимости от того, как данный тип сигнала работает в текущем режиме

**Критерий успеха:** В БД есть regime для сделок; отчёты и веса учитывают режим.

## 🎯 Этап 5 — Разделение слоёв Intelligence (рефакторинг)

**Цель:** Чёткое разделение: сбор сигналов → нормализация → Decision Engine → Risk Engine → Presentation (Telegram). Без смешивания доменной логики и форматирования.

### Шаги

1. [ ] **SignalCollector:** Вынести сбор всех сигналов в отдельный модуль/класс
2. [ ] **DecisionEngine:** Агрегация, конфликты, направление, сила, уверенность — без риска и без форматирования
3. [ ] **RiskEngine:** SL/TP, размер позиции, уровни риска — на входе рекомендация от Decision, на выходе обогащённая рекомендация
4. [ ] **Presentation:** Форматирование для Telegram (format_intelligence_message и т.п.) только в одном месте
5. [ ] **Тесты:** Юнит-тесты на DecisionEngine и RiskEngine по примерам вход/выход

**Критерий успеха:** Изменение весов или риска не требует правок в 1850-строчном монолите; тесты проходят.

## 🎯 Этап 6 — ML как probability enhancer

**Цель:** ML не «предсказывает цену», а оценивает P(win | features) и ожидаемое R по фичам (тип сигнала, режим, волатильность и т.д.) на основе накопленных исходов.

### Шаги

1. [ ] **Фичи:** Из закрытых сделок формировать датасет: features (signal_type, regime, strength, confidence, volatility, …), target (TP=1, SL=0 или R_multiple)
2. [ ] **Модель:** Обучение на истории; предсказание вероятности TP и/или ожидаемого R для новой рекомендации
3. [ ] **Интеграция:** Результат ML использовать для корректировки confidence или веса сигнала в DecisionEngine
4. [ ] **Переобучение:** Периодическое переобучение по новым закрытым сделкам

**Критерий успеха:** Новые рекомендации получают ML-скор; качество метрик (expectancy, Sharpe-like) можно сравнить до/после.

## 🎯 Этап 7 — Два режима работы (скан vs глубина)

**Цель:** Явно разделить сценарии: (A) скан всего рынка — поиск возможностей, ранжирование; (B) глубокий анализ выбранной пары — отчёт, режим, история сигналов и эффективность по паре.

### Шаги

1. [ ] **Скан:** Отдельный поток/команда — сбор сигналов по списку пар, ранжирование по силе/expectancy, вывод топа без полной рекомендации по каждой
2. [ ] **Глубокий анализ:** Текущий `/intelligence SYMBOL` и AI-меню — полная рекомендация + регистрация в симуляции + при желании история по этой паре из simulated_trades
3. [ ] **Watchlist:** Опционально — список «любимых» пар пользователя с приоритетом в скане и отдельными уведомлениями

**Критерий успеха:** Пользователь может и «просканировать рынок», и «получить полный разбор по одной паре» без смешивания логики.
